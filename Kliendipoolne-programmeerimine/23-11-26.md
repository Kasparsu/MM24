## 🗂️ Topics Covered

> 🎨 The verdict is in: most of the framework reports picked **Nuxt UI**, so it went onto
> `main`. This lesson installed it, built a header with navigation, met TypeScript types for
> the first time, filled the front page with fake blog posts from **Faker**, and then tried
> to fetch real posts from the Laravel backend. That ran straight into **CORS**, which led to
> Laravel's API routes and CORS config.

### 1. 🏆 The framework pick: Nuxt UI

Of those who actually did the comparison and branch tasks, most said **Nuxt UI** is the most
sensible choice for the blog right now. Not the only truth, it has its own quirks, but it is
made by the Nuxt team, so it fits the project best. From now on `main` uses it
(<https://nuxt.com/modules/ui>, docs at <https://ui.nuxt.com/>).

### 2. 📥 Installing Nuxt UI

The install is short: Nuxt UI is a Nuxt **module** and is styled with **Tailwind CSS**. The
same "functional reading" as last week: the docs show a config, we already have one, so look
at what is there (the `export default` and the existing keys) and add only the missing parts:

```ts
  compatibilityDate: '2025-07-15',
  devtools: { enabled: true },
  telemetry: false,
  modules: ['@nuxt/ui'],
  css: ['~/assets/css/main.css'],
});
```

and a new `app/assets/css/main.css` that pulls in Tailwind and Nuxt UI's styles:

```css
@import "tailwindcss";
@import "@nuxt/ui";
```

### 3. 🧭 Header, navigation and a container

The menu came from the docs' header example. Everything goes inside `<UApp>` (like
Vuetify's `<v-app>`), `<UHeader>` holds the title, the navigation menu and, on the right, a
dark mode toggle and a GitHub button. `<UContainer>` around the page keeps the content from
running edge to edge:

```vue
<template>
  <UApp>
    <UHeader title="Blog">
      <UNavigationMenu :items="items" />

      <template #right>
        <UColorModeButton />

        <UTooltip text="Open on GitHub" :kbds="['meta', 'G']">
          <UButton color="neutral" variant="ghost" to="https://github.com/nuxt/ui" target="_blank"
            icon="i-simple-icons-github" aria-label="GitHub" />
        </UTooltip>
      </template>
    </UHeader>
    <NuxtRouteAnnouncer />
    <UContainer>
      <NuxtPage />
    </UContainer>
  </UApp>
</template>
```

The example's logo slot was dropped, `title="Blog"` is enough for now. The cat and kitten
pages from the routing lesson were deleted (their job was to show how routes work), and the
plain `<ul>` menu went with them. The old `Btn` component stays in `components/` for now.

### 4. 🔷 A first look at TypeScript

The docs' `<script>` is not plain JavaScript but **TypeScript** (`lang="ts"`):

```ts
<script setup lang="ts">
import type { NavigationMenuItem } from '@nuxt/ui';

const route = useRoute();

const items = computed<NavigationMenuItem[]>(() => [
  {
    label: 'Docs',
    to: '/docs/getting-started',
    active: route.path.startsWith('/docs/getting-started'),
  },
```

TypeScript is JavaScript plus **types**: you can still write plain JS in it, and when the code
is built the types are stripped away. `NavigationMenuItem[]` says the menu is a list of
objects of a known shape: which keys they may have and what type each key is (some are
booleans, some are objects with keys of their own). Ctrl+click on the type to read it.

What that gives you in practice: start typing a new key in a menu item and the editor already
suggests the allowed ones, and if you put a wrong type somewhere (a number where a label must
be text) it tells you before the browser does. The teacher's view: plain JavaScript is fine
for small and medium projects you do alone; for big projects with many parts, and in teams,
TypeScript's checks and autocomplete are worth it, and many places prefer it.

### 5. 📰 Blog posts with fake data

Further down the docs there is not only a single blog post component but a whole
**`UBlogPosts`** list, which is exactly what the front page needs. The backend is not
connected yet, so the docs example's three posts were taken first, and then the list was
filled with **Faker** (<https://fakerjs.dev/>), the same library the Laravel seeders use. Faker
exists in almost every language, and the JavaScript one works in the frontend too:

```ts
<script setup lang="ts">
import type { BlogPostProps } from '@nuxt/ui'
import { faker } from '@faker-js/faker';

const posts = ref<BlogPostProps[]>([
  {
    title: 'Nuxt Icon v1',
    description: 'Discover Nuxt Icon v1!',
    image: 'https://nuxt.com/assets/blog/nuxt-icon/cover.png',
    date: '2024-11-25'
  },
  // ... two more from the docs
]);
for(let i=0; i<20; i++){
    posts.value.push({
        title: faker.lorem.sentence(5),
        description: faker.lorem.paragraph(),
        image: faker.image.url({width:1280,height:720}),
        date: faker.date.past(),
    });
}
</script>
<template>
  <UBlogPosts class="lg:grid-cols-4">
    <UBlogPost
      v-for="(post, index) in posts"
      :key="index"
      v-bind="post"
    />
  </UBlogPosts>
</template>
```

`posts` is a `ref`, so inside the script it is `posts.value`. `v-bind="post"` hands every key
of the object to the component as a prop. Faker's lorem, image and date helpers cover what a
post card needs (`date.past()` is always some date in the past, `date.future()` one ahead).
The grid showed three cards per row; `lg:grid-cols-4` (a Tailwind class) makes it four on
wide screens.

Why this matters: one exam part for this module is a **static frontend page**, not yet
connected to a database, that looks like the blog's design. Copy-pasting posts by hand works,
but Faker fills a page with realistic content in a few lines.

A side lesson in git: Faker got installed in the middle of the Nuxt UI work and ended up in
the "Add nuxtUI" commit. Commit **more often**, as soon as one thing is done, so each commit
is about one change.

### 6. 🪟 Front and back in separate windows

To get real posts, the Laravel project `mm24blog` had to run as well. You could open the
parent folder with both projects in one VS Code window, but the editor can get confused about
paths and imports when two projects live together. Two separate VS Code windows, one per
project, is the tidier way.

### 7. 🚧 Fetching posts, and CORS

Nuxt's data fetching page (<https://nuxt.com/docs/4.x/getting-started/data-fetching>) offers
`$fetch` (and `useFetch`). The first try just asked the Laravel server for its front page:

```ts
let data = $fetch('http://localhost:8000/')
```

The console filled with errors, and the important one was that access to `localhost:8000`
from `localhost:3000` was blocked by **CORS** policy (touched on last year too). Both servers
are on our own machine, but the port numbers differ, so the browser treats them as two
different sites. It would be a scary internet if any page could freely send requests to any
other site, so the browser only allows it when the **other server says it is fine**, by
sending the right `Access-Control-Allow-...` headers back.

### 8. 🔌 Laravel API routes and CORS config

Things change between versions, so check the docs of the version in use (Laravel 13 here,
not 11): <https://laravel.com/framework/docs/13.x/routing#api-routes> and
<https://laravel.com/framework/docs/13.x/routing#cors>.

Laravel's CORS config is not published by default; `php artisan config:publish cors` creates
`config/cors.php`. The key line is the first one: CORS headers are sent only for paths that
start with `api/`, which is reasonable, but none of our routes do:

```php
    'paths' => ['api/*', 'sanctum/csrf-cookie'],

    'allowed_methods' => ['*'],

    'allowed_origins' => ['*'],
```

Laravel used to ship an API routes file; now `php artisan install:api` adds it. It installed
**Sanctum** (which will later give the frontend a working login), registered the file in
`bootstrap/app.php` and created `routes/api.php`:

```php
        web: __DIR__.'/../routes/web.php',
        api: __DIR__.'/../routes/api.php',
        commands: __DIR__.'/../routes/console.php',
```

Every route in `routes/api.php` automatically starts with `/api`, so `/posts` there is
`/api/posts`. The first API route reuses the existing controller:

```php
Route::get('/posts', [PublicController::class, 'index']);
```

and the frontend now asks that address:

```ts
let data = $fetch('http://localhost:8000/api/posts')
```

At the very end something broke in the backend after the installs, and some students had
`composer` trouble too (closing servers and editors that may keep files locked, then running
`composer install` again, usually helps). The rest continued in the afternoon lesson.

## ✅ Takeaways

1. **Nuxt UI** won the comparison and is now on `main`: a Nuxt module styled with Tailwind.
2. **Add only the missing parts** of a docs config to your own `nuxt.config.ts`.
3. **`<UApp>`, `<UHeader>`, `<UNavigationMenu>`, `<UContainer>`** give the page its frame.
4. **TypeScript** is JavaScript plus types: autocomplete and early errors, most useful in big or team projects.
5. **Faker** works in the frontend too: realistic demo posts for a static page in a few lines.
6. **Commit often**, one finished thing per commit.
7. **CORS**: a different port is a different site, and the backend must allow the request.
8. **`install:api`** adds `routes/api.php` (every route under `/api`), **`config:publish cors`** adds `config/cors.php`.
