### 1. 🧱 Why a separate frontend?

So far the blog is one Laravel application: the server talks to the database and also renders
every view. That works, but it has two weak spots:

- **Every click reloads the whole page.** On a fast connection it is barely visible, but slow
  the network down in the browser's dev tools and you see each view being built from scratch.
  (Side note: the placeholder photo service the seeders use for images is currently down, so
  missing pictures are not your bug.)
- **One app is rarely enough.** Bigger systems usually also want a mobile app, maybe a smart
  watch app and so on. If the frontend is separate and only talks to the backend through
  requests, every client can use the same backend.

It also works the other way round: if the backend gets rewritten in some better or faster
technology, but still answers the same requests in the same format, the frontend does not
have to change at all. With everything glued together, like now, swapping the backend means
rewriting all the views too.

### 2. 🟩 Nuxt 4 and a new project

Last year the class assembled a Vue app by hand and added the router themselves. Nuxt
(<https://nuxt.com/>) is a framework on top of Vue where those decisions are already made:
routing, folder layout, build and dev server come ready. The price is reading more
documentation, the gain is fewer chances to build something odd yourself.

The project was created following the installation guide
(<https://nuxt.com/docs/4.x/getting-started/installation#create-a-new-project>): the
**minimal** template, **bun** as the package manager, and a git repository initialised by the
installer (it does not create a GitHub repo, only the local one). Optional modules were
skipped for now. The starting `app/app.vue` is tiny:

```vue
<template>
  <div>
    <NuxtRouteAnnouncer />
    <NuxtWelcome />
  </div>
</template>
```

Nuxt asks about sending anonymous telemetry on every start. One line in `nuxt.config.ts` makes
it stop asking:

```ts
export default defineNuxtConfig({
  compatibilityDate: '2025-07-15',
  devtools: { enabled: true },
  telemetry: false,
})
```

### 3. 🗺️ A tour of the generated files

- **`.nuxt/` and `.output/`**: hidden folders (the dot) with Nuxt's own generated files for the
  dev server and the build. Not something to edit, and both are in `.gitignore`.
- **`node_modules/`**: all installed packages, Nuxt and Vue included. The same idea as Laravel's
  `vendor/` folder: other people's code, never committed.
- **`public/`**: served as is, here `favicon.ico` and `robots.txt` (the file that tells search
  engine robots which pages they may visit).
- **`bun.lock`**: exact installed versions, like `composer.lock`, so everyone gets the same ones.
- **`package.json`**: dependencies and scripts. `dev` starts the development server that reloads
  on every file change, `build` makes the production version, `generate` makes static pages
  and `preview` shows the built production version.
- **`app/`**: the folder we actually work in.

Nuxt DevTools are built in: the small floating button at the bottom of the page opens them.
Last year the Vue devtools needed a separate browser plugin (it still works too).

### 4. 🧩 Components without imports

A component goes into `app/components/`, named with a capital letter. A deliberately simple
one, `Btn.vue`:

```vue
<template>
    <button>Hello</button>
</template>
```

In plain Vue it would have to be imported before use. Nuxt finds everything in `components/`
and imports it automatically, so a page can just write `<Btn></Btn>`.

### 5. 📄 Pages: routing by files

Instead of writing a router config, make an `app/pages/` folder
(<https://nuxt.com/docs/4.x/directory-structure/app/pages>). Every `.vue` file in it becomes a
page and its path comes from the file name. `index.vue` is the front page:

```vue
<template>
    <p>Hello NUXT!!!!</p>
    <Btn></Btn>
</template>
```

`cats.vue` is served at `/cats`. For pages to show at all, `app.vue` swaps `<NuxtWelcome />`
for `<NuxtPage />`, the spot where the current page is rendered.

![Kombucha](https://api.memegen.link/images/kombucha/Writing_the_router_config_by_hand/Just_drop_a_file_into_pages~s.png)

### 6. 🔗 A menu with NuxtLink

To get around without typing addresses, `app.vue` got a simple menu. A list keeps the links
apart, since there is no CSS framework yet:

```vue
<nav>
  <ul>
    <li><NuxtLink to="/">home</NuxtLink></li>
    <li><NuxtLink to="/cats">cats</NuxtLink></li>
    <li><NuxtLink to="/kittens">kittens</NuxtLink></li>
    <li><NuxtLink to="/kittens/nuustik">Nuustik</NuxtLink></li>
    <li><NuxtLink to="/kittens/anycatnamehere">any cat name</NuxtLink></li>
  </ul>
</nav>
```

Plain `<a href>` links work too, but the browser then loads the whole page again on every
click. `NuxtLink` still renders a normal `<a>` (look in the inspector), wrapped so that the
click's default action is prevented and JavaScript swaps only the page content while the
address changes. Nothing is reloaded, and it is faster.

![Roll safe](https://api.memegen.link/images/rollsafe/Can't_reload_the_whole_page/if_NuxtLink_only_swaps_the_content.png)

### 7. 🐱 Nested and dynamic routes

Folders inside `pages/` become path segments:

- `pages/kittens/index.vue` is `/kittens`,
- `pages/kittens/nuustik.vue` is `/kittens/nuustik`,
- `pages/kittens/[name].vue` matches **any** other `/kittens/...` address.

The square brackets are a route parameter, the same idea as `{post}` in a Laravel route. The
value is in `$route.params`:

```vue
<template>
    <p>Here is {{ $route.params.name }}!</p>
</template>
```

`/kittens/nuustik` still goes to its own file, since a fixed name wins over the parameter.
Anything else, say `/kittens/miisu`, prints "Here is miisu!". Brackets work on folders as
well, and the docs show more complex patterns (optional and catch-all parameters).

![Cat names everywhere](https://api.memegen.link/images/xy/Cat_names/Cat_names_everywhere.png)

### 8. 🎨 Vue component frameworks and the first task

Earlier projects used CSS frameworks (Bulma, Bootstrap, daisyUI on Tailwind). They describe
the looks well, but anything interactive (for example a menu that scrolls sideways on a phone)
needs extra JavaScript on top. A **component framework** ships finished Vue components
(buttons, menus, dialogs, tables) with both the styling and the behaviour, ready to combine and
reuse. A list of popular Vue component frameworks was shared in the chat; some work with any
Vue app, some are made for Nuxt.

**Homework:** the Teams task "Vue komponendiraamistike võrdlus ja valik mm24blog-front jaoks"
(due 20.11): study at least 5 Vue component frameworks and answer the Forms questions for each
(how it works with Nuxt, how components are styled, which blog components exist, pros and
cons), then recommend one with reasons. Read the docs, it is fine to make notes first. The
class's answers decide which framework the blog frontend will be rebuilt with.

## ✅ Takeaways

1. **A separate frontend** reloads less, can share one backend with mobile and other apps, and survives a backend rewrite.
2. **Nuxt** is Vue with routing, folders and build already decided; read the docs.
3. **Don't touch** `.nuxt/`, `.output/` or `node_modules/`; the work happens in `app/`.
4. **`telemetry: false`** in `nuxt.config.ts` stops the question on every start.
5. **Components in `app/components/`** are imported automatically.
6. **Files in `app/pages/` are routes**: `index.vue` is the folder's front page, `<NuxtPage />` shows the current one.
7. **`NuxtLink` instead of `<a href>`** swaps the content without reloading the page.
8. **`[name].vue`** is a dynamic route; read it with `$route.params.name`.
9. **Homework**: compare at least 5 Vue component frameworks in the Forms task (due 20.11).
