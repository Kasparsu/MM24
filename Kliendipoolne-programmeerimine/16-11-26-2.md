### 1. 🌿 A branch per experiment

The usual development way to test something: try it for real, because the docs do not tell
you everything (outdated pages, plugins that broke last week, odd details). Branches were
covered last year in the git lessons and are used constantly in real work.

A new branch for the experiment, `vuetify_test`, was made from the VS Code branch button in
the bottom left corner ("Create new branch"). From the command line it would be
`git switch -c vuetify_test` (or `git checkout -b`). Everything committed there stays off
`main`.

### 2. 📥 Installing Vuetify into an existing Nuxt project

Vuetify's install page starts with creating a **new** project, but we already have one, so
the useful parts are "Existing projects"
(<https://vuetifyjs.com/en/getting-started/installation/#existing-projects>) and, for Nuxt,
"Manual setup" (<https://vuetifyjs.com/en/getting-started/installation/#manual-setup>).
The packages that ended up in `package.json`:

```json
"dependencies": {
  "@mdi/font": "^7.4.47",
  "nuxt": "^4.6.4",
  "vue": "^3.5.45",
  "vue-router": "^5.4.0",
  "vuetify": "^4.3.3"
},
"devDependencies": {
  "vite-plugin-vuetify": "^2.1.3"
}
```

`@mdi/font` is the Material Design Icons font that Vuetify's icons use. Then `nuxt.config.ts`.
The docs show a whole config file, and the trick is to read it the way you read a diff: take
only what we do not have yet (the import at the top, the `build` and `vite` parts) and add it
to our own config instead of overwriting it:

```ts
import vuetify, { transformAssetUrls } from 'vite-plugin-vuetify';
// https://nuxt.com/docs/api/configuration/nuxt-config
export default defineNuxtConfig({
  compatibilityDate: '2025-07-15',
  devtools: { enabled: true },
  telemetry: false,
  build: {
    transpile: ['vuetify'],
  },
  vite: {
    plugins: [
      vuetify({ autoImport: true }),
    ],
    vue: {
      template: {
        transformAssetUrls,
      },
    },
  },
});
```

`autoImport: true` lets every `v-...` component be used without importing it, the same way
Nuxt does with our own components.

### 3. 🔌 The plugin, and the folder that was wrong

Vuetify is switched on by a Nuxt plugin. There was no plugins folder, so one was created,
with the file from the docs:

```ts
// import this after install `@mdi/font` package
import '@mdi/font/css/materialdesignicons.css'

import 'vuetify/styles'
import { createVuetify } from 'vuetify'

export default defineNuxtPlugin((app) => {
  const vuetify = createVuetify({
    // ... your configuration
  })
  app.vueApp.use(vuetify)
})
```

The page then failed: the Vuetify components were "missing template or render function", in
other words Vue had no idea what they were. Some searching found the cause: the docs were
written for Nuxt 3, but in **Nuxt 4 the plugins folder lives inside `app/`**, like `pages/` and
`components/`. The first `plugins/` folder was in the project root, so Nuxt never loaded it.
Moved to `app/plugins/vuetify.ts`, everything worked. A good example of why you try things
instead of trusting the docs blindly.

### 4. 🧭 The menu as Vuetify tabs

The plain `<ul>` menu was replaced with a component from the docs. The first candidates were
just dropdown menus or full app layouts; the tabs example "align tabs with title"
(<https://vuetifyjs.com/en/components/tabs/#align-tabs-with-title>) was close to what a blog
needs. The example came wrapped in a card, which made the menu look boxed in, so the card was
dropped and only the toolbar kept. Everything goes inside `<v-app>`, Vuetify's root element:

```vue
<template>
  <v-app>

    <v-toolbar color="primary">
      <v-app-bar-nav-icon></v-app-bar-nav-icon>

      <v-toolbar-title>Your Dashboard</v-toolbar-title>

      <v-btn icon="mdi-magnify"></v-btn>

      <v-btn icon="mdi-dots-vertical"></v-btn>

      <template v-slot:extension>
        <v-tabs
          v-model="tab"
          align-tabs="title"
        >
          <v-tab
            v-for="(url, name) in items"
            :key="name"
            :text="name"
            :value="name"
            :to="url"
          ></v-tab>
        </v-tabs>
      </template>
    </v-toolbar>

    <NuxtRouteAnnouncer />
    <NuxtPage />

  </v-app>
</template>
```

Remember the example also had a `<script setup>` part: copying only the template is not
enough, since the tabs need the `tab` variable.

**`to` instead of `href`.** Vuetify components accept `href`, which would be an ordinary link
and reload the page. Their docs say that with a router they also take `to`, which works like
`NuxtLink`: the content changes without a reload.

### 5. 🗂️ Links as an object

Instead of writing five `<v-tab>` elements, the links went into one object where the **key is
the label and the value is the address**:

```vue
<script setup>
 import { ref } from 'vue'

  const tab = ref(null)

  const items = {
    'Home': '/',
    'Cats': '/cats',
    'Kittens': '/kittens',
    'Nuustik': '/kittens/nuustik',
    'any cat name': '/kittens/anycatnamehere',
  }
</script>
```

The first try printed the addresses as labels. When `v-for` goes over an object, the
**value comes first** and the key second: `(url, name) in items`, not `(name, url)`. After
swapping them (and one browser refresh) the tabs showed the right names and led to the right
pages.

### 6. 🔀 Switching branches back and forth

The work was committed and the branch pushed (publishing a new branch creates it on GitHub
too). Then the payoff: switch back to `main` (the same branch button, or
`git switch main` / `git checkout main`) and the Vuetify menu is gone, the plain menu is back.
Nothing is lost: switch to `vuetify_test` and it all returns. A new branch for the next
framework starts from `main` again, clean.

One catch: `node_modules` is not in git, so switching branches does not change the installed
packages. Coming back to `main` with Vuetify still in `node_modules`, or going to a branch that
needs packages you installed elsewhere, can break the dev server in confusing ways. After
every switch, run `bun install` so the installed packages match that branch's `package.json`
again (bun also removes what is no longer listed).

### 7. 📱 Why bother with a separate frontend (again)

To close, a recap of the first lesson's point: a frontend that only talks to the backend
through requests can share that backend with a mobile app or anything else, and if the
backend is ever rewritten to answer in the same format, the frontend does not notice.

## ✅ Takeaways

1. **Try frameworks for real**, each on its own branch made from `main`.
2. **Merge, don't overwrite**: take only the missing parts of the docs' `nuxt.config.ts`.
3. **Nuxt 4 plugins go in `app/plugins/`**; in the root they are silently ignored.
4. **Copy the `<script setup>` too**, not just the template of a docs example.
5. **Use `to`, not `href`**, on framework links so the router handles them.
6. **`v-for` over an object** gives `(value, key)`, value first.
7. **`bun install` after every branch switch**, since `node_modules` is not in git.
