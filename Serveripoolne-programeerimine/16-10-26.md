### 1. 🏔️ Alpine.js and typosquatting

After the database was recreated, everyone had to register again, and with email verification
switched on last time, the verification link was fetched from the end of
`storage/logs/laravel.log`. The profile page then complained that it cannot import Alpine.

Breeze's original views (the profile page in particular) use **Alpine.js**
(<https://alpinejs.dev/>), a tiny JavaScript library for small bits of logic straight in the
HTML. It is a little like Vue, but without any `.vue` files or build-time components. Breeze
installed it, and we removed it together with the rest of Breeze's frontend. We do not really
need it ourselves, but as long as the given views use it, it has to be installed again:

```json
"dependencies": {
    "alpinejs": "^3.17.4"
}
```

The package is `alpinejs`, without a dot. Typing `bun i alpine.js` by accident led to a
detour about **typosquatting** (<https://en.wikipedia.org/wiki/Typosquatting>). Big companies
buy up every domain one typo away from theirs, smaller sites cannot, so a mistyped address can
lead to a lookalike page serving viruses or spyware. The same trick is played with packages: a
package named one letter away from a popular one can contain code that listens to what users
type into your site (passwords, card numbers), and package managers can run scripts on install.
A mistyped `composer` command really has pulled malware onto a school computer before. So check
the package name (look it up, or ask) before installing, and if something odd got installed,
`bun remove` it right away.

![Typosquatting](https://api.memegen.link/images/inigo/bun_i_alpine.js/I_do_not_think_that_package_is_what_you_think_it_is.png)

### 2. 🏠 Home instead of the dashboard

The Breeze dashboard is useless for our blog, but after registering or logging in Breeze sends
you there. The redirects live in the controllers in `app/Http/Controllers/Auth`: one controller
per action, split up more finely than ours, and not always with the clearest names. In
`RegisteredUserController` the `store()` method validates the name, email and password, creates
the user, fires the `Registered` event, logs the user in, and redirects:

```php
return redirect(route('home', absolute: false));
```

The same change, `dashboard` to `home`, went into every place that redirects there:
`AuthenticatedSessionController` (after login), `ConfirmablePasswordController`, and the three
email verification controllers:

```php
return redirect()->intended(route('home', absolute: false));
```

`intended()` sends the user back to the page they originally tried to open (for example one
behind the `auth` middleware), and only falls back to the given route if there was none.

### 3. 🧑 Who is logged in: `@auth` and a dropdown

Logged in, the menu still offered Register and Login. Blade's **`@auth`** directive is an `if`
that already checks whether someone is logged in; `@else` covers the guest, and **`@guest`**
also exists for the opposite check.

For the logged in case the menu gets a daisyUI dropdown. The first attempt (a whole menu with a
submenu copied from the navbar) ran off the right edge of the page, so the
**dropdown aligned to the end** was used instead
(<https://daisyui.com/components/dropdown/#dropdown--aligns-to-end-of-button-horizontally>),
which opens towards the left.

The button shows the user's name. `auth()` on its own does not give the user, `auth()->user()`
does. Logging out has to be a `POST` with the CSRF token (Breeze's own navigation has the same
form), so the form and its button went straight into the list item, and they fit fine where a
link would normally be. Profile stays as an ordinary link:

```html
@auth
    <div class="dropdown dropdown-end">
        <div tabindex="0" role="button" class="btn m-1">{{ auth()->user()->name }}</div>
        <ul tabindex="-1" class="dropdown-content menu bg-base-100 rounded-box z-1 w-52 p-2 shadow-sm">
            <li><a href="{{ route('profile.edit') }}">Profile</a></li>
            <li>
                <form method="POST" action="{{ route('logout') }}">
                    @csrf
                    <button>Logout</button>
                </form>
            </li>

        </ul>
    </div>
@else
    <a href="{{ route('register') }}" class="btn btn-primary">Register</a>
    <a href="{{ route('login') }}" class="btn btn-secondary">Login</a>
@endauth
```

### 4. 🌱 A seeder for users

Every `migrate:fresh --seed` brings the posts back, but your own user is gone and you have to
register again. Laravel already ships a `UserFactory`, and `DatabaseSeeder` had two commented
out lines that use it. Rather than leave them there, they got their own seeder, made with
`php artisan make:seeder UserSeeder` (singular, like `PostSeeder`). The command writes the class,
the namespace and an empty `run()` for us:

```php
public function run(): void
{
    User::factory(10)->create();

    User::factory()->create([
        'name' => 'Test User',
        'email' => 'test@example.com',
    ]);
}
```

The editor underlined `User` until `App\Models\User` was imported. `DatabaseSeeder` now calls
both seeders, users first on purpose: right now the order does not matter, but posts are about to
need users.

```php
$this->call(UserSeeder::class);
$this->call(PostSeeder::class);
```

After `php artisan migrate:fresh --seed` the `users` table has 11 rows: ten random ones and the
test user.

### 5. 🔑 Your own default user from `.env`

`test@example.com` is not something your browser offers to fill in. While developing, the
server always runs on the same address and port, so it is nicer to have a user whose email and
password are already in your fingers. Writing your own name, email and password into the seeder
is a bad idea, though: the file goes into git, and in a team everyone would keep overwriting it
with their own details.

The place for such things is **`.env`**, which is not committed and already holds secrets like
keys and passwords. New keys can be added at the end, and `.env.example`, which *is* committed,
gets the same keys with harmless placeholder values so that the next developer knows they exist.
Nothing real or secret goes into `.env.example`. (Placeholder names like John Doe come from the
nameless bodies in crime shows; here it is User McUserface.)

```dotenv
DEFAULT_USER_NAME="User McUserface"
DEFAULT_USER_EMAIL=user@user.user
DEFAULT_USER_PASSWORD_HASH=
```

Values with spaces need quotes. The seeder reads them with `env()`, whose second argument is the
fallback when the key is not set:

```php
'name' => env('DEFAULT_USER_NAME', 'User McUserface'),
'email' => env('DEFAULT_USER_EMAIL', 'user@user.user'),
'password' => env('DEFAULT_USER_PASSWORD_HASH', Hash::make('password')),
```

Why a **hash** and not the password itself? Even in `.env` a plain password is not really safe:
a colleague asks to see your `.env`, you share your screen in a meeting, you stream. A hash can
be shown to anyone; with a long enough password, brute forcing it back takes a very long time.

The hash was made with **`php artisan tinker`**, an interactive PHP shell with the whole Laravel
app loaded: models, factories, facades. `App\Models\Post::factory()->make()` there builds a post
without saving it (`make` vs `create`), and `Hash::make('...')` prints a hash. Copy it into
`.env`, and put it in quotes: hashes are full of `$` signs, which `.env` otherwise treats
specially, and logging in did not work until the quotes were added.

![Hash in .env](https://api.memegen.link/images/harold/Sharing_my_screen_with_.env_open/At_least_the_password_is_only_a_hash.png)

### 6. 🔁 A seeder you can run twice

`migrate:fresh --seed` drops everything first, so the seeder always runs on empty tables. A plain
`php artisan migrate --seed` keeps the data and runs the seeders again, and then creating the
default user fails on the **unique** email. The ten random users do not clash, because the
factory asks Faker for `unique()->safeEmail()`; with that many possible addresses a collision is
very unlikely. Our default email is always the same, so the seeder checks first. The email went
into a variable so it is not written twice, and since we only care whether the user *does not*
exist, there is no need to `get()` or `first()` it, `exists()` with a `!` is enough:

```php
User::factory(10)->create();
$defaultUserEmail = env('DEFAULT_USER_EMAIL', 'user@user.user');
if(!User::where('email', $defaultUserEmail)->exists()) {
    User::factory()->create([
        'name' => env('DEFAULT_USER_NAME', 'User McUserface'),
        'email' => $defaultUserEmail,
        'password' => env('DEFAULT_USER_PASSWORD_HASH', Hash::make('password')),
    ]);
}
```

Now the seeders can be run again and again (the users and posts just keep adding up).

### 7. 🔗 Posts belong to users: a foreign key

A post should have an author. Storing the author's **name** in the posts table is a poor idea:
it is long, the name is already in the `users` table, and names are not unique (think how many
people are called Jaanus Tamm). The `id` is unique and a small number, so the post stores the
user's id in a column of the same type: `id()` is an auto incrementing unsigned big integer, so
`user_id` is an unsigned big integer (not auto incrementing).

That alone lets the database end up in a wrong state: a post can point at a user that does not
exist, or a user can be deleted while their posts stay behind. A **foreign key** rules this out:
the database refuses a `user_id` that is not in `users`, and refuses to delete a user who still
has posts. To be able to delete such a user, `onDelete('cascade')` makes the database delete
their posts too: the **cascade effect**, better known as the domino effect. The long way:

```php
// $table->unsignedBigInteger('user_id');
// $table->foreign('user_id')->references('id')->on('users')->onDelete('cascade');
```

The long form is there for when you need something non-standard. For the usual case Laravel has
a short one: `foreignIdFor()` takes the model, and from it works out the column name `user_id`
and the type. `constrained()` adds the actual foreign key to the `users` table, and
`cascadeOnDelete()` is the same as `onDelete('cascade')` without a string to mistype:

```php
$table->foreignIdFor(User::class)->constrained()->cascadeOnDelete();
```

### 8. 🎲 Seeding posts with random authors

After `migrate:fresh` the post seeder failed: `user_id` cannot be null, and the post factory does
not fill it. Passing `['user_id' => 1]` to `create()` works, but then every post belongs to the
same user, which is poor test data.

Better: `make()` the posts without saving, loop over them, give each one a random existing user
and save it by hand. The first version asked the database for each post:
`User::inRandomOrder()->first()` (most databases can return rows in random order, handy for
things like "featured posts"). It works, but it is one query per post, 1000 queries. That only
makes sense with very many users and very few posts; we have the opposite.

So all users are fetched **once**, and the random pick happens in PHP. What Eloquent returns is
not a plain array but a **Collection**: it works like an array, but has methods on it (like
objects in JavaScript or Python) instead of the long list of `array_*` functions of plain PHP.
`random()` gives one random item (`random(3)` would give three). And since only the id matters,
`select('id')` loads just that column instead of names, emails and password hashes:

```php
$users = User::select('id')->get();
$posts = Post::factory(1000)->make();
foreach($posts as $post) {
    $post->user_id = $users->random()->id;
    $post->save();
}
```

Now the posts have `user_id` values from 1 to 11.

### 9. 🤝 Relationships in the models

To use the link in code, both models describe it. A post has one `user_id`, so it has one user,
and the method reads like the sentence "a post belongs to a user". No import is needed: `User`
and `Post` are in the same namespace (`App\Models`), which usually means the same folder.

```php
public function user() {
    return $this->belongsTo(User::class);
}
```

The other direction is useful too (a profile page listing someone's posts, for example). A user
can have many posts, so the method name is plural:

```php
public function posts() {
    return $this->hasMany(Post::class);
}
```

On the home page each card now shows its author. `user` is used **without parentheses**, like
`snippet`: `$post->user` gives the related `User` model (with parentheses you would get the
relationship query instead). The text is dimmed with daisyUI's `text-base-content` at 70%
opacity:

```html
<span class="text-base-content/70">{{ $post->user->name }}</span>
```

## ✅ Takeaways

1. **Breeze's profile views need Alpine.js**: `bun i alpinejs`, and always double check a package name before installing.
2. **Breeze redirects to `dashboard`** from the auth controllers; point them at `home`.
3. **`@auth` / `@else` / `@endauth`** (and `@guest`) switch the menu; `auth()->user()->name` is the logged in user, and logout is a `POST` form with `@csrf`.
4. **`make:seeder`** for users, called before the post seeder.
5. **Personal defaults go into `.env`**, placeholders into `.env.example`; store a password **hash** (made in `tinker`), in quotes.
6. **Check with `exists()` before creating** so seeders can run more than once.
7. **`foreignIdFor(User::class)->constrained()->cascadeOnDelete()`** links posts to users and keeps the database consistent.
8. **Fetch once, pick in PHP**: `select('id')->get()` and the collection's `random()`, not a query per post.
9. **`belongsTo` and `hasMany`** describe the relationship; `$post->user->name` without parentheses.
