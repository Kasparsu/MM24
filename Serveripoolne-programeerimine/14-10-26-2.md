## 🗂️ Topics Covered

> 🔐 A tour of everything Breeze added: registration, login, the dashboard, the profile page and
> password reset. Its views are built from Blade components and do not use our layout, so login
> and register were rewritten in plain Blade with daisyUI. Then email verification and a page
> that asks for the password again. The rest of the views are the homework.

### 1. 🧭 What Breeze gives us

A walk through the new pages. **Register** creates a user and logs them straight in, landing on
the **dashboard**. The **profile** page lets the user change their name and email, change the
password, and delete the account. **Log out** brings you back to the start, **Log in** works
with the account just created, and **Forgot your password?** sends a reset link by email.

Everything works, but it does not look like our site: the forms have Breeze's own styling, the
inputs do not look like daisyUI's, and our menu is gone on all of these pages.

### 2. 🧩 Where the views come from: Blade components

Breeze put its views in `resources/views/auth`, `profile`, `layouts` and `components`. Opening
`login.blade.php` shows something new:

```html
<x-guest-layout>
    <!-- Session Status -->
    <x-auth-session-status class="mb-4" :status="session('status')" />

    <form method="POST" action="{{ route('login') }}">
        @csrf

        <!-- Email Address -->
        <div>
            <x-input-label for="email" :value="__('Email')" />
            <x-text-input id="email" class="block mt-1 w-full" type="email" name="email" :value="old('email')" required autofocus autocomplete="username" />
            <x-input-error :messages="$errors->get('email')" class="mt-2" />
```

These `x-` tags are **Blade components**, a style closer to Vue than to the `@extends` and
`@section` we have used so far. Each one is a file in `resources/views/components`;
`<x-text-input>` is just an input with Breeze's classes merged into whatever attributes you pass.
The page frame is the `guest` layout, and the form lands where it prints `{{ $slot }}`.

It is a fine way to build an app, but it means a second system of layouts and components next
to ours. To keep the project simple, we rewrite the views to what we already know.

### 3. 🎨 Login and register in plain Blade and daisyUI

The `<x-guest-layout>` wrapper becomes our layout, which also brings our menu back:

```html
@extends('partials.layout')
@section('content')
    <div class="container mx-auto">
```

Each label, input and error component becomes the same fieldset we built for the post form: a
`legend`, an `input` with `w-full`, `old()` for the value, and `@error` for the red border and
the message. The texts stay translatable with `@lang`:

```html
<fieldset class="fieldset">
    <legend class="fieldset-legend">@lang('Email')</legend>
    <input name="email" value="{{ old('email') }}" type="email"
        class="input w-full @error('email') input-error @enderror" required autocomplete="username" />
    @error('email')
        <p class="label text-error">{{ $message }}</p>
    @enderror
</fieldset>
```

The form became the same centred card as the post form
(`card bg-base-300 shadow-sm w-2/3 mx-auto p-3`), the "Remember me" checkbox a daisyUI
`checkbox` in its own fieldset, the "Forgot your password?" link a `btn btn-link`, and the
submit button a `btn btn-primary`. Register got the same treatment for its four fields.

The `autocomplete` attributes were kept on purpose. `username` and `current-password` tell the
browser's password manager this is a login form, so it offers the saved login; `new-password` on
the register form makes it offer to generate and save a strong password instead.

![Rewrite](https://api.memegen.link/images/ive/x--text--input/input_class=input_w--full.png)

The menu's placeholder button made way for the two new pages:

```html
<div class="navbar-end gap-2">
    <a href="{{ route('register') }}" class="btn btn-primary">Register</a>
    <a href="{{ route('login') }}" class="btn btn-secondary">Login</a>
</div>
```

### 4. 📬 Password reset without a mail server

"Forgot your password?" says the link was sent, but no email arrives. The project has no real
mail server: `MAIL_MAILER=log` in `.env` makes Laravel write every email into the log instead.
At the end of `storage/logs/laravel.log` (where our earlier errors are too) is the whole
message, reset link included. Open the link, set a new password, and log in with it.

![Mail log](https://api.memegen.link/images/dwight/MAIL__MAILER=log/The_reset_link_is_in_laravel.log.png)

### 5. 🛡️ Confirm password and verify email

Breeze has two more features that are there but not switched on.

**Confirm password**: some pages should ask for the password again even from a logged in user
(think of a bank, or changing important settings). The `password.confirm` middleware does that.
A test page, `/secure`, shows the home page behind it:

```php
Route::get('/secure', [PublicController::class, 'index'])->name('secure')->middleware(['auth', 'password.confirm']);
```

Logged out, it sends you to log in first (`auth`); logged in, it asks for the password before
letting you through, and does not ask again for a while.

**Verify email**: the `User` model already had the line, commented out. Uncommenting the import
and implementing the interface is all it takes:

```php
use Illuminate\Contracts\Auth\MustVerifyEmail;
```

```php
class User extends Authenticatable implements MustVerifyEmail
```

Now a user who has not verified their address is stopped at a "verify your email" page (the
dashboard route has the `verified` middleware) with a button to send the link again. The link
is, again, in `laravel.log`.

![Confirm password](https://api.memegen.link/images/persian/Opening_~ssecure/Confirm_your_password_first.png)

### 6. 📝 Homework: the rest of the auth pages

The point of all this: login and register now look like our site, but the other Breeze pages
(forgot, reset and confirm password, verify email, the profile and the dashboard) still use the
components. The homework (Teams assignment **"Auth pages rewrite in daisyui"**, due 21.10) is
to rewrite the remaining Breeze views from Blade components to plain Blade with daisyUI, the
same way login and register were rewritten in class: `forgot-password`, `reset-password`,
`confirm-password`, `verify-email`, `profile/edit` with its three partials, and `dashboard`.
The profile page is a little more involved (several forms, and a delete confirmation), and the
assignment has detailed instructions.

## ✅ Takeaways

1. **Breeze gives working auth**: register, login, logout, profile, password reset, email verification.
2. **`x-` tags are Blade components** from `resources/views/components`; we swap them for our layout and daisyUI fieldsets.
3. **Keep `autocomplete`** (`username`, `current-password`, `new-password`) so password managers work.
4. **`MAIL_MAILER=log`**: emails, with their links, end up in `storage/logs/laravel.log`.
5. **`password.confirm` middleware** asks for the password again on sensitive pages.
6. **`implements MustVerifyEmail`** on `User` turns on email verification.
