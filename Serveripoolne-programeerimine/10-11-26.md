## 🗂️ Topics Covered

> 👥 The blog gets a social side: users can follow each other. That is a many to many
> relationship again, but this time between users and users, so the pivot table needs its own
> column names. On top of it: a follow/unfollow button that toggles, follower counts on the
> user page, a seeder, and a **Feed** page with posts only from the people you follow.

### 1. 🪪 A header on the user page

Clicking an author already showed that user's posts, through `PublicController@user` and the
`welcome` view. Now the view also gets the user itself, so it can show who this page is about:

```php
return view('welcome', compact('posts', 'user'));
```

The same `welcome` view is also the home page, where there is no `$user`, and reading a missing
variable is an error. So the user card is wrapped in `@isset`: if the variable is set, show the
card, otherwise do not even try to read it.

```html
@isset($user)
    <div class="card bg-base-300 shadow-sm my-2">
        <div class="card-body">
            <h1 class="card-title">{{ $user->name }}</h1>
            ...
        </div>
    </div>
@endisset
```

### 2. 🔁 Following: many to many from users to users

A user can follow many users and be followed by many users. Same shape as posts and tags, only
both sides are the same table. Like any many to many, it needs a pivot table.

It could be done with a model, but a plain table is enough, so only a migration was made
(`php artisan make:migration create_follows_table`). Since this is not a model, nobody fills the
`id` or timestamps, so they were removed. What is left is two foreign keys to `users`:

```php
Schema::create('follows', function (Blueprint $table) {
    $table->foreignIdFor(User::class, 'follower_id')->constrained()->cascadeOnDelete();
    $table->foreignIdFor(User::class, 'followee_id')->constrained()->cascadeOnDelete();
    $table->unique(['follower_id', 'followee_id']);
});
```

Plain `foreignIdFor(User::class)` twice would name both columns `user_id`, and a table can not
have two columns with the same name. So each gets its own name: **`follower_id`** is the one who
follows, **`followee_id`** the one being followed.

The `unique` pair came a bit later: at first, pressing "Follow" again simply added a second,
identical row. A row like that should never exist, and the database itself can forbid it, just
like `post_tag` did. After adding it the table had to be migrated again.

### 3. 🔀 `belongsToMany` with the column names spelled out

The table is not called `user_user` and the columns are not `user_id`, so Laravel can not guess
anything. `belongsToMany` takes the table name and the two pivot columns: first the column that
points to *this* model, then the column that points to the related one.

```php
public function followers() {
    return $this->belongsToMany(User::class, 'follows', 'followee_id', 'follower_id');
}

public function followees() {
    return $this->belongsToMany(User::class, 'follows', 'follower_id', 'followee_id');
}
```

Read `followers()` as: "find rows where **I** am the `followee_id`, and give me the users in
`follower_id`". `followees()` is the same the other way round.

This is exactly the place to get confused. The first version had the two columns swapped, and
only looking at the table after a test follow showed it: user 11 (the logged in one) stood as
the one *being* followed. Swapping the arguments fixed it. When a self referencing relationship
is in doubt, follow once and look at the row.

### 4. ❓ "Have I followed this user?"

The button should say *Follow* or *Unfollow*, so the view needs to know whether the logged in
user already follows this one. That became an attribute accessor on `User`:

```php
public function authHasFollowed(): Attribute {
    return Attribute::get(function (){
        if(!Auth::check()){
            return false;
        }
        return $this->followers()->where('follower_id', Auth::user()->id)->exists();
    });
}
```

- **`exists()`**: we do not care about the row itself, only whether there is one. The database
  answers with just true or false.
- **`Auth::check()` first**: after a reseed we were logged out, and the page crashed with
  "property id on null", because `Auth::user()` is `null` for a guest. Two fixes were compared.
  `Auth::user()?->id` (the nullsafe operator from an earlier lesson) also works, but still sends a
  pointless query looking for follower `null`. Returning `false` right away when nobody is logged
  in gives the same result without touching the database.

In the view, `$user->authHasFollowed` picks the button:

```html
<form action="{{route('follow', $user)}}" method="POST">
    @if($user->authHasFollowed)
        <button class="btn btn-error">Unfollow</button>
    @else
        <button class="btn btn-primary">Follow</button>
    @endif
</form>
```

### 5. 🔘 One route that toggles

Instead of separate follow and unfollow routes, forms and controller methods, there is one. It
looks at the current state and does the opposite:

```php
public function follow(User $user) {
    if($user->authHasFollowed) {
        $user->followers()->detach(Auth::user());
    } else {
        $user->followers()->attach(Auth::user());
    }
    return redirect()->back();
}
```

```php
Route::post('/user/{user}', [PublicController::class, 'follow'])->name('follow')->middleware('auth');
```

Two separate routes would also need guarding: what if someone (a clever user or a "hacker")
sends a follow for a user they already follow, or an unfollow for one they never followed? With
the toggle that situation simply can not happen. `detach()` is the opposite of `attach()`: it
removes the pivot row. The `auth` middleware sends a guest to the login page, and
`redirect()->back()` returns to the page the button was on.

### 6. 🔢 Follower counts

The user card shows how many followers and followees the user has:

```html
<span class="text-base-content/70"><b>Followers:</b> {{ $user->followers()->count() }}</span>
<span class="text-base-content/70"><b>Followees:</b> {{ $user->followees()->count() }}</span>
```

Note the **parentheses**: `followers()` returns the query, and `count()` on it asks the database
for just a number. We do not need to know who the followers are, so there is no reason to load
them all.

One more thing noticed: right now a user can follow themselves. It does no harm, and the button
is easy to hide when the page is your own, but forbidding it in the database is harder. Left as is.

### 7. 🌱 `FollowSeeder`

There is no `Follow` model, so no factory either: the users already exist, the seeder only
connects them. For every user, a random number of random users (from none to all) become its
followers:

```php
$users = User::select('id')->get();
foreach($users as $user){
    $randUsers = $users->random(rand(0, $users->count()));
    $user->followers()->attach($randUsers);
}
```

`random()` on a collection never returns the same item twice, so the unique pair is not broken.
The seeder was called right after `UserSeeder` in `DatabaseSeeder`, so it runs early and any
problem shows up at once instead of after all the posts are generated.

### 8. 📰 The Feed

The last piece: a page with posts only from the people you follow. A route with the `auth`
middleware (a guest has no followees) and a **Feed** link in the navigation inside `@auth`:

```php
Route::get('/feed', [PublicController::class, 'feed'])->name('feed')->middleware('auth');
```

A "has many through" relationship (posts through followees) was tried first, but it needs a model
for the middle table and `follows` has none. So `User` got a `feed()` method that collects the ids
of the followees and asks for posts whose author is one of them:

```php
public function feed() {
    $followeeIds = $this->followees()->select('id')->get()->pluck('id');
    return Post::whereIn('user_id', $followeeIds);
}
```

- **`pluck('id')`** turns the collection of users into a plain list of ids.
- **`whereIn`** is SQL's `IN`: the column must match one of the values in the list.

`feed()` returns a query, not results, so the controller can chain the usual eager loading,
ordering and pagination onto it and reuse the `welcome` view:

```php
$posts = Auth::user()->feed()->with('images', 'user', 'tags')->withCount('comments')->latest()->simplePaginate(16);
```

Unfollowing someone makes their posts disappear from the feed at once.

## ✅ Takeaways

1. **Users following users is many to many** within one table: a `follows` pivot, no model needed.
2. **Name the two keys yourself**: `foreignIdFor(User::class, 'follower_id')` and `'followee_id'`.
3. **`belongsToMany(User::class, 'follows', 'followee_id', 'follower_id')`**: this model's column first, the related one second. Check a real row when in doubt.
4. **`unique(['follower_id', 'followee_id'])`** stops double follows in the database.
5. **`authHasFollowed`** with `exists()`, and `Auth::check()` first so guests cost no query.
6. **One toggling route** (`attach` or `detach`) is simpler and safer than two.
7. **`followers()->count()`** counts in the database instead of loading everyone.
8. **Feed**: `pluck('id')` the followees, then `Post::whereIn('user_id', ...)`, returned as a query to paginate.
