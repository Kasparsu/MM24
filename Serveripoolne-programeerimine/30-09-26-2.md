## 🗂️ Topics Covered

> 🧂 The morning explained why passwords must be hashed. This lesson does it in two lines,
> then moves on to the other classic form problem: uploading a file without one user
> overwriting another's.

### 1. 🔐 `password_hash()` and `password_verify()`

PHP has bcrypt built in. On registration:

```php
$user->password = password_hash($_POST['password'], PASSWORD_BCRYPT);
```

`PASSWORD_BCRYPT` is a constant: no dollar sign, all capitals, a fixed value. There are
other algorithms and options (like the cost) but the defaults are fine.

On login, comparing strings no longer works, because the same password gives a different
hash every time. `password_verify()` does the comparison:

```php
if(!$user || !password_verify($_POST['password'], $user->password)) {
    return redirect('/login');
}
```

Mind the `!`: `password_verify()` returns `true` when the password matches, and this `if`
is the "send them back" branch, so it needs the opposite. Writing it without the `!` at
first meant the wrong password got in and the right one did not.

The old users had plain text passwords, which can never pass `password_verify()`, so the
users table was emptied and an account registered again. In the database the password
column now holds a `$2y$...` bcrypt hash. (There is no minimum length check yet; there
should be.)

### 2. 📎 A file field and `enctype`

The article form got an image field:

```php
<div class="mb-3">
  <label for="image" class="form-label">Image</label>
  <input name="image" type="file" class="form-control" id="image">
</div>
```

Submitted as it was, `$_POST` only contained the file's **name** and `$_FILES` was empty.
The very common mistake: a form sends `application/x-www-form-urlencoded` by default, which
can only carry text. Files need:

```php
<form action="/admin/articles" method="POST" enctype="multipart/form-data">
```

"Multipart" means the request has several parts: the ordinary fields, plus the file.
Nobody remembers the exact string; the editor suggests the three options once you type
`enctype="`.

![enctype](https://api.memegen.link/images/mmm/Forgets_enctype_on_the_form/Wonders_why_$__FILES_never_gets_the_file.png)

### 3. 🗂️ What `$_FILES` holds, and where the file goes

`$_FILES['image']` has the original `name`, the `type`, a `tmp_name`, an `error` code and
the `size`. The file itself sits in a temporary folder, and PHP **deletes it when the
request ends**. Otherwise anyone could fill the server's disk by uploading files that
nobody keeps. To keep it, move it:

```php
move_uploaded_file($tmp, $uploads . $filename);
```

The destination is `public/uploads/`, inside the public folder so the images can be shown
later. Uploaded files do not belong in git, so the folder has its own `.gitignore`:

```
*
!.gitignore
```

Ignore everything here, except this file, so the empty folder itself still exists in the
repo.

### 4. 🖼️ Why the original filename is a trap

The cautionary tale: a private photo gallery stored uploads under their original names.
Cameras name files `IMG_0001.jpg` and so on, so two different people uploaded different
photos with the same name, the second upload replaced the first, and the first person's
gallery suddenly showed someone else's picture. Moral: never trust the user's filename to
be unique.

![Same name](https://api.memegen.link/images/disastergirl/Two_parents_upload_IMG__0001.jpg/Only_one_picture_survives.png)

### 5. 🎲 A unique name

```php
$tmp = $_FILES['image']['tmp_name'];
$ext = pathinfo($_FILES['image']['name'],PATHINFO_EXTENSION);
$uploads = __DIR__ . '/../../public/uploads/';
do {
    $filename = md5($_FILES['image']['name'] . microtime() . rand(PHP_INT_MIN, PHP_INT_MAX)) . ".$ext";
} while(file_exists($uploads . $filename));
move_uploaded_file($tmp, $uploads . $filename);
```

- **`pathinfo(..., PATHINFO_EXTENSION)`** keeps the extension (`jpg`, `png`) so the file
  still works as an image.
- The name is an MD5 of the original name, the current time in microseconds and a random
  number. MD5 is bad for passwords but perfectly fine for making a random-looking name.
- **`do { } while (file_exists(...))`**: a collision is less likely than being hit by a
  meteorite, but if the name is taken anyway, generate a new one. A do-while loop always
  runs at least once, which is exactly what is needed here.

Now uploading the same picture twice gives two different files. If the original name is
needed later (for a download, say), it can be stored in the database next to the new one.
The `dd()` used while testing was removed afterwards, so creating articles works again; the
file is saved but not yet linked to the article.

## ✅ Takeaways

1. **`password_hash()` to store, `password_verify()` to check.** Never compare hashes yourself.
2. **File upload = `type="file"` + `enctype="multipart/form-data"`**, or nothing arrives.
3. **Uploaded files vanish at the end of the request** unless you `move_uploaded_file()` them.
4. **Never keep the user's filename.** Generate a unique one and keep the extension.
5. **Uploads stay out of git**: `*` and `!.gitignore` in the folder's own ignore file.
