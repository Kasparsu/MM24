## 🗂️ Topics Covered

> 🗂️ The blog gets categories. They look a lot like tags, but a post has exactly one category
> (or none), so this is a plain foreign key on `posts`, not a pivot table. Along the way: how to
> add a column to an existing table with a migration that can be rolled back, posts without a
> category and the null safe operator `?->`, and finally subcategories, where a category points
> to another category in the same table.

### 1. 🏷️ Categories vs tags

Categories are another very common feature: blogs have them, and web shops are where they get
really deep (clothing, then women's clothing, then trousers, then jeans). The usual difference
from tags:

- a post can have **many tags**;
- a post has **one category**.

People do sometimes build "categories" that allow several per item, but then they are really
tags under another name. A category needs little more than a name. The name is not made unique
here, since in a deeper tree the same name ("Trousers") can legitimately appear under different
parents.

The classes came from the usual all in one artisan command (model, migration, factory, seeder,
policy, resource controller and form requests) in the "Generate Category classes" commit, and the
factory got a random word as the name:

```php
'name' => fake()->unique()->word
```

### 2. 🧱 Adding `category_id` to posts the proper way

Since a post belongs to one category, the foreign key goes into the `posts` table. The quick
idea is to add the line to the old posts migration. That has two problems: the posts migration
runs **before** the categories table exists, so the foreign key would point to a table that is
not there yet, and on a live system you can not just wipe the database and rerun everything.

The proper way is to change the existing table from a **new** migration. The categories migration
now does two things in `up()`, and undoes both in `down()`, in reverse order:

```php
public function up(): void
{
    Schema::create('categories', function (Blueprint $table) {
        $table->id();
        $table->string('name');
        $table->timestamps();
    });

    Schema::table('posts', function (Blueprint $table) {
        $table->foreignIdFor(Category::class)->nullable()->constrained()->cascadeOnDelete();
    });
}

public function down(): void
{
    Schema::table('posts', function (Blueprint $table) {
        $table->dropForeignIdFor(Category::class);
    });
    Schema::dropIfExists('categories');
}
```

- **`Schema::table`** (not `Schema::create`) modifies a table that already exists.
- **`down()` must be the exact opposite of `up()`**: if this migration is rolled back, the column
  on `posts` has to go too, otherwise the old table keeps a column pointing at a table that no
  longer exists.
- The new column ends up last in the table. People like `created_at` and `updated_at` at the end,
  but the column order makes no real difference.
- There is also `php artisan make:migration` for writing such a migration on its own, without a
  model.

### 3. 🕳️ Posts without a category: `nullable()`

The `posts` table already has rows, and the column is new, so what goes into it for the existing
posts? A required foreign key would need a valid category for every one of them. The simplest
choice here: a post **does not have to** have a category, so the column is `nullable()`.

The relationships are the familiar one to many pair:

```php
// Category.php
public function posts() {
    return $this->hasMany(Post::class);
}
```

```php
// Post.php
public function category() {
    return $this->belongsTo(Category::class);
}
```

`category` is singular on the post, because a post has at most one.

### 4. 🌱 Seeding categories, in the right order

`CategorySeeder` just makes ten categories. In `DatabaseSeeder` it has to run **before**
`PostSeeder`, because the posts need existing categories to point to. Put it at the end and
every post gets `null`, and you wonder why.

```php
$this->call(UserSeeder::class);
$this->call(CategorySeeder::class);
$this->call(PostSeeder::class);
```

`PostSeeder` associates a random category with most posts, the same way it associates the user:

```php
$categories = Category::select('id')->get();
// ...
$post->user()->associate($users->random());
if(rand(0,9)) {
    $post->category()->associate($categories->random());
}
```

`rand(0,9)` gives a number from 0 to 9. Every number except 0 counts as true in the `if`, so in
about nine cases out of ten the post gets a category, and roughly a hundred of the thousand posts
stay uncategorized. A quick way to have both cases in the test data.

### 5. ❓ Showing the category: the null safe operator

The category goes on the post card as a badge. The first try,
`$post->category->name`, crashed on the uncategorized posts: `$post->category` is `null` there,
and `null` has no `name`. The fix is the **null safe operator** `?->`, which JavaScript and many
other languages have as optional chaining:

```html
<div class="badge badge-secondary">{{ $post->category?->name ?? 'Uncategorized' }}</div>
```

- **`?->`**: if the left side is `null`, stop and give `null` instead of an error; otherwise read
  `name` as usual.
- **`?? 'Uncategorized'`**: the null coalescing operator from earlier. If the result is `null`,
  show this text instead of an empty badge.

### 6. 🌳 Subcategories: a table that points to itself

How would subcategories work? The beginner idea is a separate `subcategories` table with its own
model. Then sub-subcategories need yet another table, and so on: it gets out of hand fast.

The neat solution is a column in `categories` that points to **another row of the same table**:
the parent category. A category without a parent is a top level one, so the column has to be
`nullable()` (the very first category can not have a parent, since nothing exists yet). This is
often called a **parent/child** relationship, and it can go as deep as you like: children,
grandchildren and so on.

```php
$table->foreignIdFor(Category::class)->nullable()->constrained()->cascadeOnDelete();
```

```php
public function parent() {
    return $this->belongsTo(Category::class);
}

public function children() {
    return $this->hasMany(Category::class);
}
```

Both relationships point to the same model: `parent()` up to one category, `children()` down to
many. The lesson ran out of time here, so this was committed as a first draft and finished in the
afternoon. One thing the draft still needed: `foreignIdFor(Category::class)` names the column
`category_id`, while `belongsTo` on a method called `parent()` looks for `parent_id`. The
afternoon lesson renamed the column to `parent_id` to make the two agree.

The same idea powers threaded comments, like on Reddit: a comment can have a parent comment.

## ✅ Takeaways

1. **Tags vs categories**: many tags per post, one category per post (a foreign key on `posts`, no pivot).
2. **Change existing tables from a new migration** with `Schema::table`, and make `down()` undo it (`dropForeignIdFor`).
3. **`nullable()`** for a foreign key that existing rows can not fill, or that is optional.
4. **Seeder order matters**: categories before posts, or every post gets `null`.
5. **`if (rand(0,9))`** is true nine times out of ten: an easy way to leave some rows empty.
6. **`$post->category?->name ?? 'Uncategorized'`**: `?->` stops at `null`, `??` gives a fallback.
7. **Subcategories** are a self referencing table: a nullable parent id, `parent()` and `children()` on the same model.
8. **Column names must match the relationship**: `parent()` looks for `parent_id` (fixed in the afternoon).
