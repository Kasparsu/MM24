## 🗂️ Topics Covered

> 📝 Getting the blog running on a new computer already takes a dozen steps, and not everyone
> had it working yet. So this lesson's task: write those steps down in the project's README.
> The taught part was short (the steps, with hints for the ones we had not seen yet); the rest
> of the lesson was independent work on the README and on getting the project running.

### 1. 📖 Why an install guide

- **For yourself**: at home, on another classroom computer, or when something breaks, the steps
  are written down instead of half remembered.
- **It is part of development.** There is always a new developer, a junior, someone who wants to
  help with the project. If the setup is not documented, they cannot even start.
- **For AI too.** We now use AI as a kind of junior developer, one that is not always the
  smartest. With a written guide it does not have to invent the steps itself.

The README that `laravel new` created was full of generic Laravel text. It was emptied and the
guide goes there instead.

![README](https://api.memegen.link/images/jim/Write_the_install_steps_into_the_README/Future_you_is_also_a_new_developer.png)

### 2. 🪜 The steps

The skeleton written on the board, committed as an example:

```markdown
1. clone project
2. winget install vscode git php 
3. bun install command from bun site
4. composer installer link 
5. php.ini extentions
6. composer install
7. bun install
8. create .env file from .env.example
9. `php artisan key:generate`
10. `php artisan migrate` (yes)
11. run laravel `composer run dev`
```

Hints for the steps we had not done yet:

- **Installing tools**: give the actual commands or links (winget for VS Code, git and PHP; the
  install command from Bun's home page; the Composer installer from its download page).
- **`php.ini` extensions**: name the exact extensions. Laravel needed some that learnphp did not,
  among them the SQLite one for the database. Nobody remembers that a month later.
- **`composer install` and `bun install`**: `install` (not `require` or `add`) brings back
  everything the project already lists, into `vendor` and `node_modules`.
- **`.env`**: it is not in git, so a clone does not have it. It is made from `.env.example`,
  either by copying the file in the editor and renaming it, or with a command
  (`cp .env.example .env`).
- **`php artisan key:generate`**: a fresh `.env` has an empty `APP_KEY`, and the app will not
  start without one.
- **`php artisan migrate`**: creates the database tables. If the SQLite file does not exist it
  asks whether to create it: yes.
- **`composer run dev`**: one command that runs everything the project needs at once (the PHP
  server and Vite), the same idea as the npm scripts last year.

### 3. ✍️ Markdown and English

The README is Markdown, so commands go in backticks: `` `php artisan migrate` `` for one inline
command, or a block between three backticks for longer ones. GitHub then shows them as code, often
with a copy button.

Write it in **English**. Everything code related (code, commit messages, READMEs) is in English,
so that any developer anywhere can help with the project. Only the content the site's users see
is in Estonian.

## ✅ Takeaways

1. **Setup steps belong in the README**, for yourself, the next developer and the AI.
2. **`.env` is not in the clone**: copy it from `.env.example`, then `php artisan key:generate`.
3. **`install` restores, `require`/`add` adds** something new.
4. **Commands in backticks, everything code related in English.**
