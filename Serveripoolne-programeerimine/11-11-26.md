### 1. 🤔 Pivot table or model?

A like connects a user and a post, so it is many to many again: a post is liked by many users, a
user likes many posts. It could be a bare pivot table like `follows` yesterday. But as soon as
likes get more interesting (see the next section), a model is the more sensible choice, so the
whole set was generated at once (model, migration, factory, seeder, policy, controller and form
requests in the "Generate likes classes" commit).

In a way a like is like a comment without text: it belongs to a user and to a post. The
difference is that one user may comment on a post many times, but may like it only once. That is
a `unique` pair again:

```php
Schema::create('likes', function (Blueprint $table) {
    $table->id();
    $table->foreignIdFor(Post::class)->constrained()->cascadeOnDelete();
    $table->foreignIdFor(User::class)->constrained()->cascadeOnDelete();
    $table->unique(['user_id', 'post_id']);
    $table->timestamps();
});
```

### 2. 👍 How other sites do likes

Before settling on the simplest version, a tour of what "like" means elsewhere. These ideas
stayed in the migration as comments:

```php
//$table->tinyInteger('value'); // -1 => dislike, 1 => like  Youtube

//$table->enum('value', ['👍', '😊', '😭', '💚', '🤬', '💩']); // facebook style reactions

// $table->string('value', 10); // discord, teams etc
// $table->unique(['user_id', 'post_id', 'value']);
```

- **YouTube: like and dislike.** Two tables would be silly, they are the same thing with a
  different sign, and one user must not have both at once. One row with a `value` column does it.
  `tinyInteger` is the smallest integer type, a single byte: -128 to 127 (0 to 255 unsigned), more
  than enough. Using **-1 for dislike and 1 for like** (rather than 0 and 1, or 1 and 2) has a
  bonus: `SUM(value)` gives a score straight away, positive when likes win, negative when dislikes win.
- **Facebook: reactions.** The default is the thumb, but you can pick one of a fixed set. An
  `enum` column only accepts values from a given list, so the database itself refuses anything else.
- **Discord, Teams: any emoji, several per user.** Here one user can add as many different
  reactions as they like, but each one only once. The value is a short string (an emoji takes
  several bytes, so not just 1), and the unique rule covers **three** columns: user, post and value.

We kept the plain version: liked or not liked.

### 3. 🌱 `LikeSeeder`

The comment seeder picked a random user for every comment, which would break the unique rule
here: the same user could be picked twice for one post. So for each post the seeder takes a
random *set* of users (`random()` never repeats an item) and creates one like per user:

```php
$users = User::select('id')->get();
$posts = Post::select('id')->get();
foreach($posts as $post) {
    $randUsers = $users->random(rand(0, $users->count()));
    foreach($randUsers as $user) {
        Like::factory(1)->create(['post_id' => $post->id, 'user_id' => $user->id]);
    }
}
```

The array passed to `create()` fills the two foreign keys, and the factory itself needs nothing.
`LikeSeeder` was called in `DatabaseSeeder` right after `PostSeeder`, early enough that a mistake
shows up before everything else is generated. DataGrip then showed the `likes` table filled for
every post.

### 4. 🔗 Relationships and the like count

The relationships were copied from comments, since they are the same shape:

```php
// Like.php
public function user() {
    return $this->belongsTo(User::class);
}

public function post() {
    return $this->belongsTo(Post::class);
}
```

```php
// Post.php and User.php
public function likes() {
    return $this->hasMany(Like::class);
}
```

The post card already showed the number of comments from `comments_count`. Likes got the same
treatment: `withCount` in every `PublicController` method that lists posts (home, user page, feed),
so the numbers come with the posts in one query instead of one extra query per post:

```php
$posts = Post::with('images', 'user', 'tags')->withCount('comments', 'likes')->latest()->simplePaginate(16);
```

### 5. 💬 A tooltip with the names of the likers

Many sites show who liked something when you hover over the count. A dropdown would need a click,
so the daisyUI **tooltip** was used instead (link in the chat). It does not have to wrap a button,
a plain `<span>` works, and its `tooltip-content` can hold any HTML, so the names can go on
separate lines.

The question was how to get from a post to the *users* who liked it. A like itself only holds
the ids. A "has many through" relationship (users through likes) was tried, but it is meant for
chains like country, users, posts, and did not fit. The working version loads the likes together
with their user:

```php
public function likedUsers() {
    return $this->likes()->with('user');
}
```

```html
<span class="text-base-content/70"><b>Likes:</b>
   <div class="tooltip">
       <div class="tooltip-content">
           @foreach($post->likedUsers as $liker)
               <div class="text-base-content/70">{{ $liker->user->name }}</div>
           @endforeach
       </div>
       <span>{{ $post->likes_count }}</span>
   </div>
</span>
```

### 6. 🔘 Like and Unlike

The button works like yesterday's Follow: one route, one method, and the method decides what to
do. The difference is that a like is a model, so instead of `attach` and `detach` a `Like` is
created or deleted:

```php
public function like(Post $post) {
    if($post->authHasLiked) {
       $like = $post->likes()->where('user_id', Auth::user()->id)->first();
       $like->delete();
    } else {
        $like = new Like();
        $like->post()->associate($post);
        $like->user()->associate(Auth::user());
        $like->save();
    }
    return redirect()->back();
}
```

`first()` is enough when looking up the like to delete, as there can only be one. The route is a
POST with the `auth` middleware, and `authHasLiked` on `Post` is a copy of `authHasFollowed`:
false for guests, otherwise `exists()` on the user's like.

```php
Route::post('/post/{post}', [PublicController::class, 'like'])->name('like')->middleware('auth');
```

On the card, the form shows **Like** or a red **Unlike**. At first every post said "Like" even
after logging in: the accessor's name did not match what the view asked for. Once the method name
and the attribute name matched, the toggle worked.

## ✅ Takeaways

1. **A like is many to many too**; a `Like` model leaves room for richer likes later.
2. **`unique(['user_id', 'post_id'])`**: one like per user per post.
3. **Like systems differ**: `tinyInteger` -1/1 for YouTube style (sum = score), `enum` for a fixed reaction set, a string plus a three column unique for Discord style.
4. **Seed with `random()` sets**, not one random user per row, when the pair must be unique.
5. **`withCount('comments', 'likes')`** gives the counts in the same query as the posts.
6. **daisyUI tooltip** with `tooltip-content` can list the likers; `likes()->with('user')` gets their names.
7. **Toggle route again**: delete the existing `Like`, or create one with `associate()`.
8. **Next**: a pass/fail understanding check in Forms, then client side programming.
