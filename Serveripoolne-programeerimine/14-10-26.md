### 1. ↩️ Keeping the user's input: `old()`

Last time the create form got validation. One thing was still wrong: leave the title empty after
writing a long body, submit, and Laravel sends you back to the form with an error, but the body
is **gone**. With two lines it does not matter much; with a long article the user would be
furious. Some browsers can bring the text back with the back button, but most users would never
think of that.

Laravel sends the previous input back along with the errors, and `old()` reads it. For an input
it goes in the `value` attribute, for a textarea between the tags. Mind the spacing in the
textarea: anything between `>` and `{{` (a newline, spaces) becomes part of the content.

```html
<input name="title" value="{{ old('title') }}" type="text" class="input w-full @error('title') input-error @enderror" placeholder="Title" />
```

```html
<textarea name="body" class="textarea h-36 w-full @error('body') textarea-error @enderror" placeholder="Some content here">{{ old('body') }}</textarea>
```

### 2. ✏️ Editing a post

The edit page is the create form again, with two differences. First, the fields start with the
post's current values. When there is no old input, `old()` returns null, and `??` (the null
coalescing operator) falls back to the value from the database:

```html
<input name="title" value="{{ old('title') ?? $post->title }}" type="text" class="input w-full @error('title') input-error @enderror" placeholder="Title" />
```

(A slip to fix in your copy: in the commit the textarea falls back to `$post->title`. It should
be `$post->body`.)

Second, the request method. Creating used POST; updating, by convention, uses **PUT** or
**PATCH**. Both are meant for updating, with a different idea behind them: PATCH sends only the
fields that changed, PUT sends the whole thing, changed or not. Our form always sends both
fields, so PUT it is.

The catch: HTML forms only know GET and POST. Write `method="PUT"` and the browser quietly falls
back to GET. So the form still says POST, and Laravel's `@method` adds a hidden field telling
Laravel which method was really meant:

```html
<form action="{{route('posts.update', $post)}}" method="POST" class="card bg-base-300 shadow-sm w-2/3 mx-auto p-3">
    @csrf
    @method('PUT')
```

```php
Route::get('/admin/posts/{post}/edit', [PostController::class, 'edit'])->name('posts.edit');
Route::put('/admin/posts/{post}', [PostController::class, 'update'])->name('posts.update');
```

`update()` gets its own form request, `UpdatePostRequest`. It needed the same treatment as the
store request: `authorize()` returns `true` with a `@todo`, and the same rules. Why two classes
if they are identical? Because they often are not: some fields may only be set when creating,
or updating may be checked differently.

The controller then has several ways to save, the first two kept as comments: set the fields one
by one, `fill()` the model and save, or do both in one call:

```php
// $post->title = $request->validated('title');
// $post->body = $request->validated('body');
//$post->fill($request->validated());
$post->update($request->validated());
return redirect()->route('posts.index');
```

### 3. 👁️ Viewing a post

The "View" button leads to `posts.show`, a zebra table with the post's id, title, content and
timestamps. Its Back button goes wherever the user came from:

```html
<a href="{{ url()->previous() }}" class="btn btn-primary">Back</a>
```

If you came from page 8 of the list, you land on page 8 again, not on the first page.

### 4. 🗑️ Deleting, and the `form` attribute

Deleting is different from View and Edit. A link can only make a GET request, and deleting must
not happen on a GET: anything that follows links (a crawler, a prefetching browser, a link
someone sends you) could delete data. Deleting gets its own method, DELETE, so it needs a form
with `@csrf` and `@method('DELETE')`:

```php
$post->delete();
return redirect()->route('posts.index');
```

Putting the form around the Delete button can upset the layout: daisyUI's `join` (and similar
groups in other frameworks) styles its direct children, and a button wrapped in a form is no
longer one. The button does not have to be inside its form, though. The `form` attribute
connects it to a form anywhere on the page by id. The id must be unique, so it includes the
post's id:

```html
<button form="delete-form-{{ $post->id }}" type="submit" class="btn btn-error">Delete</button>
</div>
<form id="delete-form-{{ $post->id }}" action="{{ route('posts.destroy', $post) }}" method="POST">
        @csrf
        @method('DELETE')
</form>
```

### 5. 🚀 Laravel starter kits

When a new Laravel project is created, the installer offers starter kits (React, Vue, Livewire)
that come with registration, login and the rest already working. We did not pick one at the
start, because they bring a lot of complexity we did not need yet. The older and simpler kit,
**Laravel Breeze**, is described in the Laravel 11 docs
(<https://laravel.com/framework/docs/11.x/starter-kits>). The newest docs no longer mention it,
but it still works with current Laravel and keeps things simple, so that is what we use.

### 6. 🧭 `Route::resource`

The seven admin routes follow a pattern Laravel knows: index, create, store, show, edit, update
and destroy, always with the same addresses, methods and names. One line registers all of them,
pointing at the resource controller's seven methods:

```php
Route::resource('/admin/posts', PostController::class);
```

The old lines stayed in `routes/web.php` as comments, to compare. Everything keeps working,
because the generated routes have exactly the names we already used (`posts.index`,
`posts.edit` and so on). For update, the resource route accepts both PUT and PATCH.

### 7. 🌬️ Installing Breeze

Breeze is a development dependency that copies its code into the project and then gets out of
the way:

```json
"laravel/breeze": "^2.4",
```

Its installer is meant for a fresh project, and ours is not. It overwrote some of our work:
`routes/web.php` lost our home page route, and the CSS was replaced with Breeze's own, so our
daisyUI theme disappeared. This is where git pays off: the diff showed exactly what had changed,
our routes and styles were put back, and only Breeze's additions were kept. The routes it adds
are the dashboard and profile, plus `require` of a separate file for all the auth routes:

```php
Route::get('/dashboard', function () {
    return view('dashboard');
})->middleware(['auth', 'verified'])->name('dashboard');

Route::middleware('auth')->group(function () {
    Route::get('/profile', [ProfileController::class, 'edit'])->name('profile.edit');
    Route::patch('/profile', [ProfileController::class, 'update'])->name('profile.update');
    Route::delete('/profile', [ProfileController::class, 'destroy'])->name('profile.destroy');
});

require __DIR__.'/auth.php';
```

The commit added close to sixty files: controllers in `app/Http/Controllers/Auth`, views in
`resources/views/auth`, `profile` and `components`, and a big pile of tests in
`tests/Feature/Auth`. It also put Alpine.js into `resources/js/app.js`, which Breeze's own views
use for dropdowns and modals. After `composer run dev` the home page and the admin posts worked
again as before. Next lesson: what all those new pages do.

## ✅ Takeaways

1. **`old()` refills a form** after a validation error; `old('x') ?? $model->x` on edit forms.
2. **HTML forms only do GET and POST**: `@method('PUT')` or `@method('DELETE')` tells Laravel the rest.
3. **PATCH sends the changes, PUT sends everything**; both mean "update".
4. **Never delete on a GET.** A form with `@csrf` and `@method('DELETE')`; the button can sit outside it with `form="id"`.
5. **`Route::resource`** registers all seven CRUD routes with the standard names in one line.
6. **Breeze gives us auth**, but its installer overwrites files: commit first, then check the diff.
