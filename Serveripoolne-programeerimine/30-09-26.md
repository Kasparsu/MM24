### 1. 🔑 The login form and checking the user

The login view is the register form minus the name field, posting to `/login`. The
controller looks the user up by email:

```php
public function login() {
    $user = User::where('email', $_POST['email']);
    $user = $user ? $user[0] : null;
    if(!$user || $user->password !== $_POST['password']) {
        return redirect('/login');
    }
    $_SESSION['userID'] = $user->id;
    redirect('/');
}
```

`where()` returns a list (it could match many rows), so if anything came back we take the
first one. We know emails are unique, but the method does not. Wrong email or wrong
password both go back to the login page.

### 2. 🍪 Remembering who is logged in

Logging in means writing the user's id into the session. Sessions only work after
`session_start()`, and we want that on every page, not just the login page, so it went to
the very top of the front controller:

```php
<?php

session_start();
```

in `public/index.php`.

### 3. 🙋 `auth()`: who is this?

```php
function auth() {
    $userID = $_SESSION['userID'] ?? null;
    if($userID) {
        return User::find($userID);
    }
    return false;
}
```

`??` reads the session key if it is set and falls back to `null` if it is not, without PHP
complaining about a missing key. A helper so that any view can ask "is someone logged in,
and who?".

### 4. 🧭 Login / logout in the navigation

```php
<?php if (auth()): ?>
  <div class="dropdown">
    <button class="btn btn-secondary dropdown-toggle" type="button" data-bs-toggle="dropdown" aria-expanded="false">
      <?= auth()->name ?>
    </button>
    <ul class="dropdown-menu">
      <li><a class="dropdown-item" href="/logout">Logout</a></li>
    </ul>
  </div>
<?php else: ?>
  <a class="btn btn-sm btn-outline-secondary" href="/register">Sign up</a>
  <a class="btn btn-sm btn-outline-primary" href="/login">Login</a>
<?php endif ?>
```

Logged in: a Bootstrap dropdown with the user's name
(<https://getbootstrap.com/docs/5.3/components/dropdowns/#single-button>). Normally it would
also hold a profile or settings link, but for now it only has Logout. Logging out is the
reverse of logging in:

```php
public function logout() {
    unset($_SESSION['userID']);
    redirect('/');
}
```

### 5. 😱 Plain text passwords

At this point the passwords sit in the database exactly as typed. That is the one thing
you never do. Two reasons:

- Databases leak: a forgotten backup, a careless developer, a hacked server.
- People reuse the same email and password everywhere. A leak from your small site is a key
  to their email, their bank and so on.

![Plain text](https://api.memegen.link/images/wddth/Storing_passwords_as_plain_text/We_don't_do_that_here.png)

### 6. 🔒 Encryption vs hashing

| | Encryption | Hashing |
|---|---|---|
| Reversible? | Yes, with the key | No |
| Used for | data in transit (everything you send over HTTPS) | passwords |
| Problem for passwords | the key has to live on the server, so whoever gets the database and the code gets everything | none of that kind |

A hash function (Estonian: *räsi*) turns any text into a fixed-looking string. The demo
used MD5 (<https://www.md5hashgenerator.com/>), which is old and no longer used for
passwords, but shows the idea:

- the same input always gives the same hash,
- you cannot run it backwards,
- change one letter and the whole hash changes, so there are no hints.

Login then works without knowing the password: hash what the user typed and compare it to
the stored hash.

### 7. 🧨 How hashes get cracked anyway

- **Brute force** with hashcat (<https://hashcat.net/hashcat/>): try every combination of
  characters, hash each one, compare. Even 4 characters meant tens of millions of
  combinations. A 6-character password suggested in class was left cracking in the
  background.
- **Dictionary attack**: try the passwords people actually use first.
  `rockyou.txt` (<https://weakpass.com/wordlists/rockyou.txt>) is about 14 million real
  passwords from an old breach, sorted by popularity. Names, `123456`, bands, celebrities:
  if a password is in there, it falls in seconds.
- **Lookup tables**: someone has already hashed huge lists and stored the results, so
  cracking is just a search. Paste an MD5 hash into <https://crackstation.net/> and the
  answer comes back instantly.

![rockyou](https://api.memegen.link/images/kermit/Your_password_is_in_rockyou.txt/But_that's_none_of_my_business.png)

### 8. 🧂 bcrypt

The answer to all three: <https://bcrypt-generator.com/>

- Hash the same password twice and you get **two different hashes** (a random salt is
  baked in), yet both still verify. Precomputed tables become useless.
- It has a **cost** setting. Each step up roughly doubles the time per hash: unnoticeable
  for one login, painful for billions of guesses. As computers get faster, the cost goes up.

Putting it into the project was left for the next lesson.

## ✅ Takeaways

1. **Logged in = user id in the session.** `session_start()` on every request, `auth()` to read it.
2. **Never store plain text passwords.** Leaks happen and people reuse passwords.
3. **Encryption is reversible, hashing is not.** Passwords get hashed.
4. **Fast hashes fall** to brute force, wordlists like rockyou and lookup tables.
5. **bcrypt is salted and slow on purpose**, and the cost can grow with hardware.
