## 🗂️ Topics Covered

### 1. 📁 Splitting the Entry Point Up

`public/index.php` had accumulated everything: the asset guard, the `dump()` helper, the
autoloader, every route with its data, and the dispatch logic — around 150 lines.

It gets cut into three files:

```
helpers.php          plain functions
routes.php           route registrations
public/index.php     bootstrap + dispatch only
```

**`helpers.php`:**
```php
<?php

function dump(...$vars) {
    echo '<pre>';
    var_dump(...$vars);
    echo '</pre>';
}
```

**`public/index.php` shrinks to a bootstrap:**
```php
require __DIR__ . '/../helpers.php';
require __DIR__ . '/../routes.php';
```

**`routes.php` holds only the route table** — the same `Router::addRoute()` calls as before,
moved out. `public/index.php` goes from ~150 lines to ~20.

> 🧠 Same instinct as the partials split: each file should have one job, and you should be
> able to guess which file to open from what you're trying to change.

### 2. 🎬 Controllers

The second commit moves the page logic out of the closures and into a class:

```php
namespace App\Controllers;

class PublicController
{
    public function index()
    {
        $title = 'World';
        $posts = [ /* … */ ];
        view('index', compact('title', 'posts'));
    }

    public function us()
    {
        $title = 'U.S';
        $posts = [ /* … */ ];
        view('us', compact('title', 'posts'));
    }
}
```

**`routes.php` collapses from 66 lines to 8:**
```php
use App\Controllers\PublicController;
use App\Router;

Router::addRoute('/', [PublicController::class, 'index']);
Router::addRoute('/us', [PublicController::class, 'us']);
```

A route is now a path plus **`[class, method]`** instead of a whole closure. `::class` gives
the fully-qualified class name as a string.

### 3. 🔀 Dispatching Both Kinds of Action

The router must now handle a closure **or** a `[class, method]` pair:

```php
$router = new App\Router($_SERVER['REQUEST_URI']);
$match = $router->match();

if ($match) {
    if (is_callable($match['action'])) {
        call_user_func($match['action']);
    } else if (is_array($match['action'])) {
        $class = $match['action'][0];
        $controller = new $class();
        $method = $match['action'][1];
        $controller->$method();
    }
} else {
    echo 404;
}
```

Note `new $class()` and `$controller->$method()` — **the class and method names are variables**.
PHP resolves them at runtime, which is the whole trick behind routing to a controller.

### 4. 👁️ A `view()` Helper

```php
function view($viewName, $variables = []) {
    extract($variables);
    include __DIR__ . "/views/$viewName.php";
}
```

Two pieces:

| Function | What it does |
|---|---|
| `compact('title', 'posts')` | Builds `['title' => $title, 'posts' => $posts]` from variable names |
| `extract($variables)` | The reverse — turns array keys back into variables |

So the controller says `view('index', compact('title', 'posts'))`, and inside `views/index.php`
the variables `$title` and `$posts` simply exist. The controller no longer needs to know where
view files live or how includes work.

**Where this has arrived:** this is **MVC** in miniature — a router mapping URLs to
controllers, controllers preparing data, and views rendering it. Every PHP framework you meet
is a more thorough version of exactly this.

## ✅ Takeaways

1. **One job per file.** `helpers.php`, `routes.php`, and an `index.php` that only boots and
   dispatches.
2. **A route can point at `[Controller::class, 'method']`**, not just a closure.
3. **`new $class()` and `$controller->$method()`** — names held in variables, resolved at
   runtime.
4. **`compact()` packs variables into an array, `extract()` unpacks them** — that pair is how
   data reaches a view.
5. **This is MVC.** Frameworks differ in thoroughness, not in shape.
