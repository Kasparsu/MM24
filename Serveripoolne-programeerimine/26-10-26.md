## 🗂️ Topics Covered

> 👤 The blog gets a public page per user: click an author's name on a post card and see only
> that author's posts. A comment counter on the cards then opened the real topic of the lesson:
> how many database queries one page makes (67!), and how `withCount()` and eager loading with
> `with()` cut that down to a handful. To finish, why `/user/2` in a URL gives away more than it
> seems, and slugs as the fix.

### 1. 👤 A public page for every user

So far the public front page shows everybody's posts, and the admin area shows only your own
after logging in. A page with one author's posts, open to everyone, takes very little: a route
with the user in it, a controller method, and the view we already have.

```php
Route::get('/user/{user}', [PublicController::class, 'user'])->name('user');
```

```php
public function user(User $user) {
    $posts = $user->posts()->latest()->simplePaginate(16);
    return view('welcome', compact('posts'));
}
```

- **`{user}` plus the `User $user` parameter**: route model binding again. Laravel takes the id
  from the URL and hands the method a ready `User`, or a 404 if there is no such user.
- **`$user->posts()`** with brackets is the relationship as a query, so `latest()` and
  `simplePaginate()` can still be added to it, just like on the front page.
- **No new view.** The method returns the same `welcome` view with the same `$posts` variable,
  so the grid of post cards and the pagination simply work.

On the post card the author's name became a link to that page:

```html
<a href="{{ route('user', $post->user) }}" class="btn btn-link">
    {{ $post->user->name }}
</a>
```

`route('user', $post->user)` gets a whole model and Laravel puts its id into the URL by itself.

### 2. 💬 Counting comments, three ways

Next, the cards should show how many comments a post has. There are three ways to get that
number, and they are very different for the database:

- **`$post->comments->count()`**: loads every comment of the post as a model, only to count them
  in PHP. Works, but asks the database for far more than we need.
- **`$post->comments()->count()`**: with brackets this is a query, and Laravel asks the database
  `count(*)`. The database sends back one number instead of all the rows. Better, but still one
  extra query per post on the page.
- **`withCount('comments')`** on the query that fetches the posts: the count is calculated in the
  same query for all posts at once, and every post gets a `comments_count` attribute.

The last one is what went into the code:

```php
$posts = Post::with('images', 'user', 'tags')->withCount('comments')->latest()->simplePaginate(16);
```

```html
<span class="text-base-content/70"><b>Comments:</b> {{ $post->comments_count }}</span>
```

### 3. 🐢 67 queries for one page: the N+1 problem

To see what is really sent to the database, an error was caused on purpose: Laravel's error page
also lists the queries the request made. It was eye opening:

- first a query for the posts, with `limit 17 offset 0`. 17, not 16, because `simplePaginate`
  fetches one extra post to know whether there is a next page;
- then, **for every post on the page separately**, a query for its images, one for its user, one
  for its tags and one for its comments.

That added up to **67 queries for a single page**. This pattern is called the **N+1 problem**:
one query for the list, then N more, one per row, every time the view touches a relationship
(`$post->images`, `$post->user`, `$post->tags`). The comment counter was only the latest addition;
the images, users and tags had been doing it all along.

The fix is **eager loading**: tell Laravel up front which relationships the page needs, and it
loads each of them with one query for all the posts on the page together:

```php
Post::with('images', 'user', 'tags')->withCount('comments')
```

Laravel collects the ids of the 16 posts and asks "give me all the images of these posts" once,
then the same for users and tags, and matches them to the right posts itself. Instead of asking
16 times "give me this post's images, now this one's", it is one question per relationship, and
the page went from 67 queries down to about five. The user page got the same treatment:

```php
$posts = $user->posts()->with('images', 'user', 'tags')->withCount('comments')->latest()->simplePaginate(16);
```

Rule of thumb: if you know the view will need a relationship for every row, load it with
`with()` in the controller instead of letting the view fetch it one by one.

🔗 [Laravel docs: eager loading](https://laravel.com/framework/docs/eloquent-relationships#eager-loading)

### 4. 🕵️ What an id in the URL gives away

The new page lives at `/user/2`, `/user/3` and so on. It works, but it says more than it should.
Ids are handed out in order, so anyone can see roughly how many users the site has, and the
**first users are usually the owner or an admin**. On a real system that is a starting point for
an attack: you know which account to go after, maybe even the person's name, and the rest can be
social engineering or worse. It sounds like an action movie, but the teacher pointed out that
such things have happened in real life, Estonia included, when a system is important enough or
someone behind it is rich enough.

Showing a name instead of a number is not a perfect secret either, but it no longer tells you
which user was first. It is also nicer: a readable address is easier to share and tells you
where a link leads before you click it.

### 5. 🐌 Slugs and spatie/laravel-sluggable

The readable part of a URL made from some text (here the user's name) is called a **slug**:
lowercase, spaces turned into dashes, special characters removed, and unique. Writing that by
hand is fiddly, so we use the `spatie/laravel-sluggable` package, which builds the slug from
another field when the model is saved and keeps it unique.

Installing it with `composer require` was started at the end of the lesson. The package, the
`slug` column and the changes to the `User` model were finished and committed in the afternoon
lesson.

## ✅ Takeaways

1. **User page**: route `/user/{user}`, `$user->posts()->latest()->simplePaginate(16)`, and the existing `welcome` view reused.
2. **`route('user', $post->user)`** takes a whole model; the author's name on the card is now a link.
3. **Counting**: `->comments->count()` loads everything, `->comments()->count()` is one query per post, `withCount('comments')` gives `comments_count` for all posts in one go.
4. **N+1 problem**: every relationship used in a loop is a query per row; one page made 67 queries.
5. **Eager loading**: `Post::with('images', 'user', 'tags')` fetches each relationship once for the whole page.
6. **Laravel's error page** lists the queries a request made, handy for spotting N+1.
7. **Ids in URLs leak information** (how many users, who came first); slugs make URLs readable and less revealing.
8. **`spatie/laravel-sluggable`** generates unique slugs; wiring it up continued in the afternoon.
