> 🗄️ The blog needs posts. This lesson goes through how Laravel builds the database: migrations

### 1. 🔎 What is already in the database

`database/database.sqlite` opened in a database viewer in VS Code already has several tables:
`users`, `sessions`, `cache`, `jobs` and others, plus one called `migrations`. They come from the
three migration files Laravel ships with. The users migration:

```php
Schema::create('users', function (Blueprint $table) {
    $table->id();
    $table->string('name');
    $table->string('email')->unique();
    $table->timestamp('email_verified_at')->nullable();
    $table->string('password');
    $table->rememberToken();
    $table->timestamps();
});
```

and the table in the viewer has exactly those columns. In bigger systems many of these
ready-made tables are needed sooner or later, so it is nice that they are already there.

The database file is not in git. To show what a fresh clone looks like, the file was deleted
(after closing the viewer's connection, which otherwise keeps it locked). `php artisan migrate`
then asks whether to create the SQLite database: yes, and it creates the file and all the tables
again.

### 2. ⏪ Running and undoing migrations

The `migrations` table is how Laravel remembers **which** migrations have already run, and in
which batch. So running `migrate` again does nothing: there is nothing new.

| Command | What it does |
|---|---|
| `php artisan migrate` | runs `up()` of every migration that has not run yet |
| `php artisan migrate:rollback` | runs `down()` of the last batch |
| `php artisan migrate:reset` | runs `down()` of all of them (the `migrations` table itself stays) |
| `php artisan migrate:refresh` | reset, then migrate |
| `php artisan migrate:fresh` | **drops every table** without running any `down()`, then migrates |

After a rollback the tables are gone (the viewer needs a refresh to show it); `migrate` brings
them back.

Why bother with `down()`? Because a live system has real data. Think of a dating app profile with
photos you spent time on: you do not want to recreate it because a developer rebuilt the
database. If a new version breaks something, the last migration can be undone in a small step,
instead of hand-editing the production database.

During development the data does not matter, so `migrate:fresh` is the one we will use the most.
It is better than `refresh` because it never runs `down()`: if a table was renamed in `up()` but
`down()` still drops the old name, `refresh` crashes on it, while `fresh` just drops everything.

![migrate:fresh](https://api.memegen.link/images/panik-kalm-panik/migrate:refresh_crashes_on_the_old_down_method/migrate:fresh_drops_every_table_anyway/Running_it_on_the_live_database.png)

### 3. 🏭 `make:model --all`

`php artisan make:` can make a migration, a model, a controller, a factory and so on one at a
time, but a model with options can make all of them at once:

```
php artisan make:model Post --all
```

The **model is singular** (`Post`: one post); Laravel names the **table plural** (`posts`) by
itself. It created:

- `app/Models/Post.php`
- `database/migrations/..._create_posts_table.php`
- `database/factories/PostFactory.php`
- `database/seeders/PostSeeder.php`
- `app/Http/Controllers/PostController.php` with all seven resource methods (`index`, `create`,
  `store`, `show`, `edit`, `update`, `destroy`), still empty
- `app/Policies/PostPolicy.php` (who may do what with posts)
- `app/Http/Requests/StorePostRequest.php` and `UpdatePostRequest.php` (form validation)

Most of these come later. They were committed right away, exactly as generated, so that our own
changes show up as separate commits afterwards.

### 4. 🧱 Columns for posts

The generated migration only has `id()` and `timestamps()`. What do those do? Ctrl+click on them
jumps deep into Laravel's code in `vendor` (read it, never change it):

- `id()` is an auto-incrementing, unsigned big integer primary key named `id`.
- `timestamps()` adds two nullable timestamp columns, `created_at` and `updated_at`, which
  Laravel fills in itself.

The posts got a title and a body:

```php
Schema::create('posts', function (Blueprint $table) {
    $table->id();
    $table->string('title');
    $table->text('body')->nullable();
    $table->timestamps();
});
```

`string` is a short text, `text` a long one. Columns are **NOT NULL by default**: if you forget a
value that must never be empty, the database refuses it, which is the safe default.
`->nullable()` explicitly allows empty, here for the body.

To apply a changed migration: roll it back and migrate again, or simply `migrate:fresh`.

### 5. 🎲 Factories and Faker

A factory describes how to make a fake post. Laravel's `fake()` helper is
**Faker** (<https://fakerphp.org/>), an ordinary PHP library that any project can use. It can
generate names, addresses, numbers, companies, and text: a word, words, a sentence, a paragraph,
paragraphs.

```php
public function definition(): array
{
    return [
        'title' => fake()->sentence(),
        'body' => fake()->paragraphs(6, true),
    ];
}
```

`paragraphs(6)` returns an **array** of paragraphs, and an array cannot go into a text column.
The second argument `true` makes it return one string instead, with the paragraphs separated by
empty lines. `id` and the timestamps are left out: the database and Laravel handle those.

### 6. 🌱 Seeders

`PostSeeder` uses the factory:

```php
public function run(): void
{
    Post::factory(1000)->create();
}
```

A thousand posts, more than we could ever type in. One seeder can be run on its own:

```
php artisan db:seed --class=PostSeeder
```

but with many seeders that gets tedious. Plain `php artisan db:seed` runs `DatabaseSeeder`, which
calls the others:

```php
// User::factory()->create([
//     'name' => 'Test User',
//     'email' => 'test@example.com',
// ]);
$this->call(PostSeeder::class);
```

Laravel's example test user had to be commented out: seeding a second time tried to create the
same user again and failed, because `email` is unique in the users table.

The command we will use all the time from now on:

```
php artisan migrate:fresh --seed
```

Drop everything, migrate, seed. It also means a fresh clone at home or in another classroom gets
the same tables and data in one command.

### 7. 🃏 Posts on the home page

With a thousand posts in the database it would be a shame not to show them. The controller gets
them with the model, the same way as in learnphp:

```php
public function index() {
    $posts = Post::all();
    return view('welcome', compact('posts'));
}
```

and the view loops over them with Blade's `@foreach`, using a daisyUI card
(<https://daisyui.com/components/card/#card>):

```html
<div class="container mx-auto">
    <h1>Home page</h1>
    @foreach ($posts as $post)
        <div class="card bg-base-100 shadow-sm my-2">
            {{-- <figure>
                <img src="https://img.daisyui.com/images/stock/photo-1606107557195-0e29a4b5b4aa.webp" alt="Shoes" />
            </figure> --}}
            <div class="card-body">
                <h2 class="card-title">{{ $post->title }}</h2>
                <p>{{ $post->body }}</p>
                <div class="card-actions justify-end">
                    <button class="btn btn-primary">Read more</button>
                </div>
            </div>
        </div>
    @endforeach
</div>
```

- `{{ $post->title }}` prints a value, like `<?= ?>` did.
- The example's shoe picture is kept for later, commented out with Blade's `{{-- --}}`.
- The card example had a fixed width, which was removed, and the cards sat against the screen
  edge. `container` limits the width and `mx-auto` centres it (horizontal margin auto).
- `my-2` adds a little vertical margin, so the cards do not touch. The same could be done with a
  gap on the container; there are several ways to do the same thing.

## ✅ Takeaways

1. **The `migrations` table remembers what has run**; `migrate` only runs what is new.
2. **`down()` matters in production; in development use `migrate:fresh --seed`.**
3. **`make:model Post --all`** creates the model, migration, factory, seeder, controller, policy and form requests. Model singular, table plural.
4. **Columns are NOT NULL unless you say `->nullable()`.**
5. **Factory = how to fake one row, seeder = how many**; Faker supplies the fake text.
6. **`Post::all()`, `compact()`, `@foreach`**: data from the model into a Blade view.
