### 2. 🛑 `dd()`: dump and die

```php
function dd(...$vars) {
    dump(...$vars);
    die;
}
```

`dump()` prints and carries on. Very often you want to look at a value and then stop
everything that comes after it, so nothing gets half-saved while you are still checking.
`die` ends the script on the spot. Same helper exists in Laravel under the same name.

### 3. 📝 Filling a model from the form

```php
public function store() {
    $article = new Article();
    $article->title = $_POST['title'];
    $article->body = $_POST['body'];
    $article->date = $_POST['date'];
    $article->author = $_POST['author'];
    $article->save();
    redirect('/admin/articles');
}
```

The controller does not write SQL. It creates an empty `Article`, fills in the fields
and asks the object to save itself. The nice part is that this reads the same for any
model: a `User` would be saved exactly the same way.

### 4. 🧬 `save()` on the base model

```php
public function save() {
    $fields = get_object_vars($this);
    unset($fields['id']);
    $db = new DB();
    $db->insert(static::$table, $fields);
}
```

- **`get_object_vars($this)`** returns the object's properties as an array:
  `['id' => null, 'title' => '...', ...]`. The model does not need to know which columns it
  has, it just hands over whatever is filled in.
- **`unset($fields['id'])`**: a new row has no id yet. The table has auto increment, so the
  database picks the id itself, and sending an empty one would only get in the way.
- Because this lives in `Model`, every model gets `save()` for free.

### 5. 🧵 Building the INSERT

The SQL we want: <https://www.w3schools.com/sql/sql_insert.asp>, and how PHP sends it:
<https://www.w3schools.com/php/php_mysql_insert.asp>

```php
public function insert($table, $fields) {
    $fieldNames = array_keys($fields);
    $fieldNamesText = implode(', ', $fieldNames);
    $fieldValuesText = implode("', '", $fields);

    $sql = "INSERT INTO $table ($fieldNamesText)
            VALUES ('$fieldValuesText')";
    $this->conn->exec($sql);
}
```

Built up one piece at a time, checking each piece with `dd()`:

1. `array_keys()` gives the column names.
2. `implode(', ', ...)` glues them into one string: `title, body, date, author`.
3. The values need quotes around each one. The trick: glue them with `', '` (quote, comma,
   space, quote) and put the outer two quotes in the SQL string itself. The double quotes
   around `"', '"` are what let the single quotes live inside.

Once the printed SQL looked right, the `dd()` came out and the row appeared in the table.

Worth remembering: the values go straight into the SQL text, so an apostrophe in a title
would break the query. Fine for learning how INSERT works, not something to ship.

### 6. 🔁 Redirect after POST

After saving, the page could just show the list. The problem: the browser's last request
was a POST, so a refresh asks "Confirm Form Resubmission", and pressing Continue sends the
same form again, creating a duplicate article. Users press Continue.

The fix is to answer the POST with a redirect, so the browser does a fresh GET to the list
page. A refresh then just reloads the list.

![Resubmit](https://api.memegen.link/images/jw/Pressing_Continue_on_Confirm_Form_Resubmission/Probably_not_a_good_idea.png)

### 7. 📨 Headers: what the browser and server tell each other

To see how a redirect works we opened the Network tab in the browser's inspector. Every
request and response has two parts: **headers** (extra information) and **body**
(the content itself).

Request headers the browser sends:

| Header | What it says |
|---|---|
| `Accept` | which content types the browser can handle |
| `Accept-Encoding` | which compression it understands (gzip and so on): the server packs the response, the browser unpacks it, which matters a lot on slow or metered connections |
| `Accept-Language` | which languages the user prefers, in order |
| `User-Agent` | which browser this is. Historically sites served different pages per browser, so every browser now claims to be all the others too |

Response headers can actually make things happen, such as `Content-Type` and
`Connection`. The one we needed is `Location`:

```php
function redirect($path) {
    header("Location: $path");
}
```

A `Location` header tells the browser to go to another address straight away. In the
Network tab you can see the POST to `/admin/articles` followed immediately by a GET to the
list. The helper exists so nobody has to type `Location: ` by hand (and typo it).

### 8. 👁️ Which article? Query parameters

The View button needs to say which article to show. Query parameters do not have to come
from a GET form: you can write them into the link yourself.

```php
<a href="/admin/articles/view?id=<?= $article->id ?>" class="btn btn-info">View</a>
```

```php
Router::get('/admin/articles/view', [ArticlesController::class, 'view']);
```

```php
public function view() {
    dump($_GET['id']);
}
```

Check the generated links with the inspector (or hover and look at the status bar) before
wondering why nothing works: one misplaced quote and the id ends up outside the `href`.
Everything in `$_GET` arrives as a string, even when it looks like a number. Actually
fetching the article by that id was left for the next lesson.

## ✅ Takeaways

1. **`dd()` = look and stop.** Check each piece of a query before letting it run.
2. **Models save themselves.** `get_object_vars()` plus `unset($fields['id'])` turns any model into an INSERT.
3. **Always redirect after a POST**, or a refresh creates duplicates.
4. **Headers are the conversation around the content.** `Location` is the one that moves the browser.
5. **Query parameters can be written into links**, and they always arrive as strings.
