## 🗂️ Topics Covered

> 🏷️ After comments, the blog gets tags. A post can have many tags and a tag can be on many
> posts, so neither a column nor a single foreign key will do: we need a many to many
> relationship with a pivot table in between. Then seeding random tags, showing them on the
> post cards, a first try at picking tags in the create form, and the Tags CRUD homework.

### 1. 🤝 A new kind of relationship: many to many

So far every relationship was one sided: a post belongs to one user, a comment belongs to one
post, an image belongs to one post. Tags are different. One post has several tags, and the
same tag sits on many posts.

The naive idea is to write the tag names into the post itself, or to give every tag row a
`post_id`. Both repeat the same tag name over and over: with a million posts, "laravel" would
be stored a million times, which wastes space and makes renaming a tag a nightmare. Each tag
should exist exactly once.

The answer is two tables: a `tags` table that is just a list of names, and a separate table
that only says "this post has that tag". That in between table is called a **pivot table**
(or intermediate table, *vahetabel*).

The classes came from the usual all in one command, which generated the model, migration,
factory, seeder, policy, resource controller and form requests in the "Generate tag classes"
commit.

![Why not both](https://api.memegen.link/images/both/Many_tags_on_one_post,_or_one_tag_on_many_posts~q/Why_not_both~q.png)

### 2. 🧩 The `tags` table and the `post_tag` pivot

The tag name is `unique()`, so the same tag can not be created twice. The pivot table went into
the same migration, right after `tags`:

```php
Schema::create('tags', function (Blueprint $table) {
    $table->id();
    $table->string('name')->unique();
    $table->timestamps();
});
// pivot-table or intermediate table, (vahe tabel)
Schema::create('post_tag', function (Blueprint $table) {
   $table->foreignIdFor(Post::class)->constrained()->cascadeOnDelete();
   $table->foreignIdFor(Tag::class)->constrained()->cascadeOnDelete();
   $table->unique(['post_id', 'tag_id']);
});
```

A few things to notice:

- **The name.** Laravel expects the two model names in singular and in alphabetical order:
  `post_tag`, not `posts_tags` or `tag_post`. Follow that and the relationship needs no extra
  configuration.
- **No `id`, no timestamps.** The pivot needs nothing but the two foreign keys.
- **`cascadeOnDelete()`** on both: deleting a post or a tag removes its rows from the pivot, but
  never the other side. Delete a tag and the posts stay, they just lose that tag.

![Pivot tables everywhere](https://api.memegen.link/images/buzz/Pivot_tables/Pivot_tables_everywhere.png)

### 3. 🔒 Unique over two columns

A post should not carry the same tag twice. Making `post_id` unique would mean a post can have
only one tag; making `tag_id` unique would mean a tag can be used on only one post. Neither is
what we want.

What we had not seen yet is that a unique rule can cover **several columns together**.
`unique(['post_id', 'tag_id'])` allows each value to repeat on its own, only the pair has to
be new:

| post_id | tag_id | |
|---|---|---|
| 1 | 1 | ok |
| 1 | 2 | ok, same post, other tag |
| 2 | 1 | ok, same tag, other post |
| 1 | 2 | refused, this pair already exists |

So the database itself guarantees there are no duplicate tags on a post, whatever the code
above it does.

![Same pair](https://api.memegen.link/images/spiderman/post__id_1,_tag__id_2/Also_post__id_1,_tag__id_2.png)

### 4. 🔗 `belongsToMany` on both sides

Earlier relationships had a `hasMany` on one side and a `belongsTo` on the other. Many to many
is symmetric, so both models get the same method:

```php
// Post.php
public function tags() {
    return $this->belongsToMany(Tag::class);
}
```

```php
// Tag.php
public function posts() {
    return $this->belongsToMany(Post::class);
}
```

Now `$post->tags` gives the tags of a post and `$tag->posts` the posts with that tag. Laravel
finds the `post_tag` table and its columns by convention.

### 5. 🌱 Seeding tags and attaching them

Tags are usually single words, so the factory uses one random word, and `unique()` on the
faker makes sure the generator does not repeat itself (the column is unique, so a repeat would
crash the seeder):

```php
'name' => fake()->unique()->word()
```

Ten unique words is no problem. Asking for a thousand could fail, since faker only has so many
words; then you would need another way to generate names.

The seeder creates ten tags, fetches only the ids of the posts, and gives every post a random
handful of them (from none to all ten):

```php
$tags = Tag::factory(10)->create();
$posts = Post::select('id')->get();
foreach($posts as $post) {
    $randomTags = $tags->random(rand(0,10));
    $post->tags()->attach($randomTags);
}
```

`attach()` is the many to many way of saving a relationship: it writes the rows into
`post_tag`, and it accepts a whole collection of models at once. `TagSeeder` was added to the
end of `DatabaseSeeder`, after the posts exist. After reseeding, the pivot table had roughly
5000 rows for the 1000 posts.

While at it, `PostSeeder` was tidied: instead of setting the foreign key by hand it now uses
the relationship, which did not exist yet when the seeder was first written:

```php
$post->user()->associate($users->random());
```

### 6. 🎫 Tags on the post card

Showing the tags is just a loop over the relationship. Each one becomes a daisyUI badge:

```html
<div>
   @foreach ($post->tags as $tag)
       <div class="badge badge-outline badge-primary">{{ $tag->name }}</div>
   @endforeach
</div>
```

daisyUI has several badge styles (outline, soft, dash, colours), pick whichever fits. The
badges first stacked under each other instead of flowing in a row, so they got their own
wrapping `<div>`.

### 7. 📋 Picking tags in the create form (unfinished)

To add tags to a new post, the form has to know which tags exist. `PostController@create`
never passed anything to its view before; now it asks the database for all tags:

```php
$tags = Tag::all();
return view('posts.create', compact('tags'));
```

The form got a `<select>` built from the daisyUI select example with a fieldset and label
(link in the chat), filled with a `@foreach` over the tags. A post needs several tags, so the
select needs the `multiple` attribute, and that is where daisyUI gave up: the single select
looks fine, but with `multiple` the styling breaks, and the current daisyUI has no multi select
component. The code was committed as is, with a comment saying so, and the select does not yet
send anything to the controller. Making it work properly is left for later.

## ✅ Takeaways

1. **Many to many** needs a third table: `tags` holds each name once, the `post_tag` pivot links posts and tags.
2. **Pivot naming**: both model names, singular, alphabetical (`post_tag`), and Laravel finds it on its own.
3. **`unique(['post_id', 'tag_id'])`** makes the pair unique, not each column: no duplicate tag on one post.
4. **`cascadeOnDelete()`** on the pivot keys: deleting a tag removes its links, never the posts.
5. **`belongsToMany`** goes on both models; save links with `$post->tags()->attach(...)`.
6. **`fake()->unique()->word()`** for a unique column, as long as you do not ask for more words than faker has.
7. **daisyUI has no multiple select**: the tag picker in the form is still unfinished.
8. **Homework**: Tags CRUD in the admin area, modelled on posts (details in Teams).
