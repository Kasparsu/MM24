## 🗂️ Topics Covered

> 🗂️ A short follow up to the morning's categories. The morning gave every category an
> optional parent, so a category can have subcategories. This afternoon the seeder learned to
> create them, the `children` relationship got the right column, and the top level categories
> appeared in the navigation bar as dropdowns. The lesson ended with the limits of that menu
> and how a recursive view would solve them.

### 1. 🏷️ Naming the parent column `parent_id`

In the morning the `categories` table got a foreign key to itself with
`foreignIdFor(Category::class)`, which names the column `category_id`. That works, but in a
table of categories a column called `category_id` says nothing about *which* category it
points to. Here it means "my parent", so the column got that name instead. `foreignIdFor`
takes the column name as a second argument:

```php
$table->foreignIdFor(Category::class, 'parent_id')->nullable()->constrained()->cascadeOnDelete();
```

For a post, `category_id` is the natural name and there is no reason to change it (you *could*
call a post's user column `author_id`, but it only adds confusion). For a table pointing at
itself, a clearer name is worth it.

The two relationships in `Category` react differently to the rename:

```php
public function parent() {
    return $this->belongsTo(Category::class);
}

public function children() {
    return $this->hasMany(Category::class, 'parent_id');
}
```

- **`belongsTo`** guesses the column from the **method name**: `parent()` means `parent_id`, so
  it already works.
- **`hasMany`** guesses from the **class name** of this model: `Category` means `category_id`,
  which no longer exists. So `children()` has to be told the column explicitly.

### 2. 🌱 Seeding categories with subcategories

Ten random categories were not enough any more: we want a tree. The seeder now creates four top
level categories and gives each of them four children:

```php
$categories = Category::factory(4)->create();
foreach($categories as $category) {
    $children = Category::factory(4)->make();
    foreach($children as $child) {
        $child->parent()->associate($category);
        $child->save();
    }
}
```

The difference between the two factory calls matters:

- **`create()`** makes the models *and saves them* to the database right away.
- **`make()`** only makes the model objects in memory. Nothing is saved yet, which gives us the
  chance to set the parent first with `associate()` and then call `save()` ourselves.

After a fresh migrate and seed, the table showed the first four rows with `parent_id` empty
(the top level ones) and the next sixteen pointing at them.

### 3. 🧭 Categories in the navigation bar

The daisyUI navbar already had an "Admin" dropdown built from `<details>` and `<summary>`. The
same structure, copied, became one dropdown per top level category. It went into the
`navbar-center hidden lg:flex` part, which is the menu shown on large screens (`lg:flex`:
hidden by default, flex from the `lg` breakpoint up), so the mobile menu does not have it yet.

The view needs the categories, but no controller passes them: the navigation is on every
page. So the query was written straight into the partial, with the full class name since the
view has no `use` line:

```html
@foreach(App\Models\Category::where('parent_id', null)->get() as $category)
    <li>
        <details>
            <summary>{{$category->name}}</summary>
            <ul class="p-2 bg-base-100 w-40 z-1">
                @foreach($category->children as $category)
                    <li><a>{{ $category->name }}</a></li>
                @endforeach
            </ul>
        </details>
    </li>
@endforeach
```

`where('parent_id', null)` picks only the top level categories, each becomes a dropdown title,
and the inner loop lists its children as the menu items. The links do not lead anywhere yet.

### 4. 🌀 Where this menu falls short

Clicking through the result works, but a few problems were pointed out:

- **Mobile**: the small screen menu has a slightly different structure and does not show the
  categories yet. Same idea, not done.
- **Only two levels**: the two `foreach` loops are written by hand, so the menu shows exactly
  two levels. A real category tree can go deeper (clothes, trousers, jeans, ...), and nesting
  more loops by hand never ends. The usual solution is a **recursive view**: a partial that
  includes *itself* for every category that has children. The teacher shared a commit from an
  earlier class's blog where exactly that was done (link below): the `categories` partial
  draws one dropdown and calls `@include('partials.categories', ...)` again for each child that
  has children of its own.
- **Posts of a parent category**: posts are attached to the lowest level. Clicking a top level
  category should probably show the posts of all its subcategories too, which needs extra
  logic in the model to collect the whole subtree.

None of this was built this time; it is there for whoever is interested.

## ✅ Takeaways

1. **`foreignIdFor(Category::class, 'parent_id')`**: give a self referencing column a name that says what it means.
2. **`belongsTo` guesses from the method name, `hasMany` from the model name**: after the rename, `children()` needs `'parent_id'` passed in.
3. **`make()` vs `create()`**: `make()` builds unsaved models, so you can `associate()` a parent before `save()`.
4. **`where('parent_id', null)`** gives the top level categories; `$category->children` gives the next level.
5. **The navigation is on every page**, so its query sits in the partial (with the full class name).
6. **Arbitrary depth needs a recursive partial** that includes itself; hand written loops stop at two levels.
